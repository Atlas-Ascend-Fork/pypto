# DSL / parser 检视规则

## 适用范围

用户 DSL 语法、解析、作用域、类型解析及从 DSL 构建 IR 的改动。
parser 只承担构建 IR 所依赖的必要优化和 lowering（如 SSA、常量折叠、函数展开）；
其他代码结构分析、优化、变换遵循 [Pass 规则](pass.md)。
若改动影响 IR 语义或后续生成代码，通过[模块索引](review-checklist.md)继续加载相关模块规则。

## 模块专属规则

### PRO-DSL-001：复用通用 AST 到 IR 的解析能力

- **适用条件**：新增 DSL 语法、AST 节点处理或解析场景。
- **检查内容**：先确认已有 parse 场景是否能够覆盖新功能；明确不能覆盖时，梳理新功能依赖的
  AST 节点场景及其到 IR 的 lowering 方式，考虑与其他 AST 结构嵌套时的行为。
  避免仅为单个语法外形另写一套已有解析逻辑。
- **报告证据**：可复用的解析入口，或不能正确处理的新 AST 场景、嵌套结构及其预期 IR。

### PRO-DSL-002：基于 IR node 的 type 校验类型

- **适用条件**：新增或修改类型相关的校验。
- **检查内容**：所有类型相关校验应基于解析后的 IR node 的 `type`，充分复用框架的 parse 能力；
  不以 AST 的表面语法或自行推断结果替代 IR 类型。tuple 类型比较同时遵循公共规则 `PRO-TUPLE-001`。
- **报告证据**：具体类型检查位置、对应 IR node/type，以及绕过现有解析能力的逻辑。

### PRO-DSL-003：普通 op 统一解析与校验分层

- **适用条件**：新增普通前端 op，或修改其参数解析、校验与消费逻辑。
- **检查内容**：按以下职责分层检视：
  1. 框架按公开 API 统一完成参数绑定校验、位置参数和关键字参数的解析及公共类型校验。
     普通参数经 `parse_expression` 解析一次；op 函数直接接收解析结果，数值、序列操作数使用 IR，
     枚举、dtype 等按框架契约保留编译期对象。不得在 op 内重新解析 AST、补做已保证的公共校验，
     或为统一路径已归一化的输入保留 Python int/list 与 IR 的双重处理。
  2. op 函数只承担本 op 的业务约束校验及 IR 构造，例如取值范围、支持的 dtype、shape 关系、
     参数组合。按 `PRO-ERROR-001` 复用公共校验原语；缺少能力时在 `ir/_utils.py` 新增有独立
     语义的接口，op 通过原语组合表达业务规则，不逐 op 复制常量取值、类型判断或容器元素校验。
     整数及整数序列原语支持上下界；整数按是否允许动态值选择 `require_int` 或
     `require_const_int`，常量整数序列使用 `require_const_int_list`；枚举用
     `require_enum(value, EnumClass)` 检查实例，不将整数隐式转为枚举。
- **报告证据**：从公开声明、dispatch 到 op 及其 helper 追踪每个参数的表示与校验责任，列出
  上游保证、业务约束、所用或缺失的原语及违规调用。仅加上 `@op_impl` 不等于完成重构。
- **边界**：只报告本次引入或扩大的问题，不借检视要求全仓迁移历史用法；历史实现和装饰器
  docstring 不能豁免新 op。默认值及独立 IR 入口按真实契约判断；允许动态值的参数不能为复用
  原语而强制常量化，也不要求所有常量都由框架提前转成 Python 值。

### PRO-DSL-004：新增前端 op 的注册与通用分发

- **适用条件**：新增或修改 op 的前端解析实现、注册方式，或在通用分发中添加 op 专属分支。
- **检查内容**：前端 op 分两类，不使用 `register_table` 或其他自行注册方式：
  1. **普通 op**：必须使用 `@op_impl`，遵循 `PRO-DSL-003` 的统一解析与校验分层约定，
     函数签名按 `PRO-DSL-006` 显式声明参数。
  2. **特殊解析 op**：只有确需处理原始 AST、统一转成普通 IR 值会丢失必要信息或改变语义时，
     才使用 `@op_impl_ast`；op 函数接收 `(self/parser, call: ast.Call)`，在实现内处理特殊语法，
     其余表达式仍复用框架解析与校验能力。对照以下现有场景核实必要性，不按 op 名称直接豁免：
     - **左值引用**：`simt.atomic_*` 需要容器及索引；普通下标解析得到的是标量 load，无法替代
       原子更新目标。
     - **上下文定型或字面量语法**：`const` 按指定 dtype 构造字面量；部分 warp 操作须先对完整
       常量表达式求值再按目标 dtype 构造。先走默认 dtype 的解析可能提前触发范围错误，
       也不能从折叠后的 IR 判断源码是否为字面量。
     - **用户定义字段**：`make_tuple`、`struct`、`struct_array` 的关键字名是数据字段，
       `self`、`span` 等不能与框架注入参数混淆；名称或长度的字面量语法约束也须保留。
     - **类型描述符结构**：`TileType` 的 shape 路径按元素解析，保留描述符用途，避免将外层
       list/tuple 物化成运行期 tuple 锚点。须证明普通值解析的具体语义影响；仅因参数是 shape、
       list/tuple 或描述符，不足以选择 AST 路径。
     需要 Python 常量、校验范围或类型、签名尚未展开、现有代码已用 AST 装饰器，均不构成例外。
  特殊处理放在对应实现中，不在 dispatch 中增加 op 专属适配；后端契约仍按 `PRO-API-001` 对齐。
  对公共 parser 按 op name 新增的拒绝分支，沿注册表、默认处理、原生 op 构造及异常传播追踪：
  不加该分支时，同一非法调用是否已由通用机制拒绝？若是，不应为新 op 枚举特殊报错；
  op 特有约束放在对应处理入口，通用层处理共性规则。与 `PRO-SIMPLE-001` 同根因合并报告。
  必须检查默认路径，不能将“未注册 Python hook”直接等同于“不支持”，因为原生 op 仍可能处理它。
- **报告证据**：解析处理函数、注册路径；使用 AST 路径时给出依赖的具体 AST 信息、
  统一解析后的表示及丢失信息或改变语义的输入例子，不能仅称“需要特殊处理”；
  专用报错分支须给出通用拒绝链和异常契约。
  拒绝发生得更早或文案更具体，本身不足以证明需要给公共框架添加 op 名单。
- **反例**：通用路径尚未覆盖的独立输入约束、必须阻止副作用的边界检查，或已明确要求的诊断契约，
  需核实后保留在恰当层；不能将所有提前校验或所有按 op 分发的合法处理一概判为冗余。

### PRO-DSL-005：类型注解的表示与消费路径

- **适用条件**：新增或修改 DSL 类型名、类型标注类、表达式 wrapper 或其解析路径。
- **检查内容**：分别追踪注解在 Python 中如何求值、parser 如何构造 IR type，以及 kernel 内的值
  实际由谁持有和消费。若 parser 直接从 AST 生成 IR 类型，后续只使用 IR Expr/type，则不能以
  注解名字需要可访问为理由，另建一套没有运行期消费者的 wrapper、构造模式和对象状态。
  只需支持注解求值时，应复用已有注解设施或保留必要的最小表示；先判断整类必要性，不能仅删除
  其中一个闲置字段或参数。Python 立即求值注解与延迟注解两条合法路径均须考虑。
  同时比较新类型与已有 DSL/IR 类型的语义：若只是在已有类型上增加标记或配置，优先扩展已有
  DSL 类型，使其与 IR 的表达一致；不要另建平行类型、解析分支及配套文档。提出独立类型时须说明
  现有表示无法表达的契约，不能把“新增名字更直观”或 PR 自行新增的说明当作必要性证明。
- **报告证据**：注解入口、AST 到 IR 的映射、实际值的表示与消费方，以及可复用类型的字段/语义。
  无用途 wrapper 与不必要的类型分裂可关联，但应分别说明；与 `PRO-DATA-001`、`PRO-SIMPLE-001`
  同根因合并，不能只报告局部冗余而漏掉整组设计问题。
- **反例**：有真实执行消费者的 Expr 包装、参与运行期 shape 绑定的注解对象，或现有类型无法表达的
  独立语义，可以有专用对象；不机械要求所有 DSL 类型与 IR 类型一一对应。删除冗余类仍须保留
  合法注解的求值能力，不能直接删名字导致函数定义报错，也不能将新类问题扩大为旧类型体系重构。

### PRO-DSL-006：op_impl 函数显式声明 API 参数

- **适用条件**：新增 `@op_impl` 对应的 op 函数，或修改其签名、参数及转发逻辑。
- **检查内容**：对照 `language/_api.py` 或对应命名空间的公开 API 声明，逐一显式写出业务参数，
  核对参数名、顺序、必填/可选、默认值语义及位置/关键字约束；允许额外的 parser 上下文和
  `span` 等框架参数，类型按解析后的实际表示标注。固定参数不得藏在 `**kwargs`、`*args` 中，
  再通过字典取值、`pop`、索引或透传恢复；通用分发已校验公开签名不能替代 op 函数的可读性要求。
  例如 API 为 `histogram(dst, src, idx, *, is_msb)` 时，op 函数也须显式声明 `is_msb`，
  不能用 `**kwargs` 接收它。
- **报告证据**：公开 API 与 op 函数的签名对照、隐藏的固定参数及读取/转发位置。
  即使调用合法、测试通过，隐藏固定参数仍作为规范违规报告。
- **边界**：公开 API 确有变长参数时保留相应语义，例如 `printf` 的格式化实参；固定参数仍须显式
  声明。本规则约束 op 函数签名，不禁止框架分发或 IR 属性构造使用字典；符合 `PRO-DSL-004`
  例外条件的 AST handler 保留 `call`，不强行展开用户定义字段。

### PRO-DSL-007：函数执行域与调用角色的完整派发

- **适用条件**：新增函数执行模式，或修改函数分类、调用合法性检查和实例化派发。
- **检查内容**：列出实际 caller 域 × callee 模式 × 入口/内部调用角色，逐格追踪分类、拦截、
  默认分支和最终 IR 调用形式；不能只验证新增模式自己的正反例。先确定外层执行域允许什么调用，
  再检查同域模式是否匹配，避免用某个新子模式的条件代替整个执行域约束。
  对共享实例化入口同时按 `PRO-FUNCTION-001`、`PRO-DATA-001` 核对类型键、常量特化及符号名，
  确认缓存中的两个不同角色或类型实例不会落到同一个外部名称。
  分类谓词按实际返回集合解释；不能从函数名中的通称推断它包含全部执行模式。
  将调用表达式的合法性与函数实例的合法性分开：关键字/展开参数语法、调用者执行域、
  形实参数量与类型匹配属于调用边界；某模式允许哪些参数种类、怎样形成签名则属于实例化。
  即使实例签名由已解析实参的类型决定，该约束也不能因此放在调用表达式的组装函数中。
  沿调用派发、实例化、缓存命中/未命中、通用函数解析逐段标出检查位置，比较同类模式的
  负责入口。实例化入口应在建立或接受实例前维护其签名约束；不在多个调用形式中重复，
  也不为专属模式向通用函数解析器添加事后回扫。是否存在第二个生产调用者不影响职责判断。
  参数数量、形实参兼容、允许的参数种类是不同谓词；已有等价检查复用，不能只移动后留下两份。
- **报告证据**：给出矩阵中的具体一格、命中的条件/默认路径、产生的调用类别及对应契约。
  同时与基线比较：既有错误单列为历史问题；新接入共同机制不完整的规范问题，指出新增的局部分支
  和其余模式为何应复用，不把历史行为伪称为本次引入。
- **反例**：有明确 ABI 或语言契约的跨域桥接、模式专属参数和不同入口允许保留差异；
  不要求所有模式拥有相同能力，也不把缺少某个组合的测试直接当作实现错误。
  调用形式确有独立的参数限制时，在调用边界检查该限制；不能将它与函数实例本身的签名约束混同。
  仅存在一个可直接调用的内部 parser 方法或手工构造测试，不足以要求新增一套防御检查。
