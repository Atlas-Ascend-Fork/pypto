# DSL / parser 检视规则

## 适用范围

用户 DSL 语法、解析、作用域、类型解析及从 DSL 构建 IR 的改动。
parser 只承担构建 IR 所依赖的必要优化和 lowering（如 SSA、常量折叠、函数展开）；
其他代码结构分析、优化、变换遵循 [Pass 规则](pass.md)。
若改动影响 IR 语义或后续生成代码，通过[模块索引](review-checklist.md)继续加载相关模块规则。

## 模块专属规则

### PRO-DSL-001：复用通用 AST 到 IR 的解析能力

- **适用条件**：新增 DSL 语法、AST 节点处理或解析场景。
- **检查内容**：先确认已有 parse 场景是否能够覆盖新功能；明确不能覆盖时，梳理新功能依赖的
  AST 节点场景及其到 IR 的 lowering 方式，考虑与其他 AST 结构嵌套时的行为。
  避免仅为单个语法外形另写一套已有解析逻辑。
- **报告证据**：可复用的解析入口，或不能正确处理的新 AST 场景、嵌套结构及其预期 IR。

### PRO-DSL-002：基于 IR node 的 type 校验类型

- **适用条件**：新增或修改类型相关的校验。
- **检查内容**：所有类型相关校验应基于解析后的 IR node 的 `type`，充分复用框架的 parse 能力；
  不以 AST 的表面语法或自行推断结果替代 IR 类型。tuple 类型比较同时遵循公共规则 `PRO-TUPLE-001`。
- **报告证据**：具体类型检查位置、对应 IR node/type，以及绕过现有解析能力的逻辑。

### PRO-DSL-003：普通 op 统一解析，消费端提取常量

- **适用条件**：新增或修改普通前端 op 的参数解析与消费。
- **检查内容**：位置参数和关键字参数均由通用 dispatch 通过 `parse_expression` 解析一次，
  传参形式遵循公开签名。实现直接接收解析结果：数值、序列操作数使用 IR；枚举、dtype 等保留编译期对象。
  需要 Python 常量时由消费端调用 `require_const_value`；整数约束复用 `require_const_int` / `require_int`。
  不保留 Python int/list 与 IR 的重复归一化分支；默认值及独立 IR 入口按其实际契约判断。
- **报告证据**：参数的解析入口、到达消费端的表示、常量提取位置，以及重复分支是否存在真实输入来源。

### PRO-DSL-004：新增前端 op 的注册与通用分发

- **适用条件**：新增 op 的前端解析实现，或在通用分发中添加 op 专属分支。
- **检查内容**：前端 op 分两类，不使用 `register_table` 或其他自行注册方式：
  1. **普通 op**：优先使用 `@op_impl`，遵循 `PRO-DSL-003` 的统一解析约定。
  2. **特殊解析 op**：仅当统一解析会丢失必要语法信息或改变参数语义时，使用 `@op_impl_ast`，
     由实现处理 AST，例如保留左值引用、按目标 dtype 构造字面量。需要 Python 常量本身不构成例外。
  特殊处理放在对应实现中，不在 dispatch 中增加 op 专属适配；后端契约仍按 `PRO-API-001` 对齐。
  对公共 parser 按 op name 新增的拒绝分支，沿注册表、默认处理、原生 op 构造及异常传播追踪：
  不加该分支时，同一非法调用是否已由通用机制拒绝？若是，不应为新 op 枚举特殊报错；
  op 特有约束放在对应处理入口，通用层处理共性规则。与 `PRO-SIMPLE-001` 同根因合并报告。
  必须检查默认路径，不能将“未注册 Python hook”直接等同于“不支持”，因为原生 op 仍可能处理它。
- **报告证据**：解析处理函数、注册路径；使用 AST 路径时说明统一解析无法保留的语义；
  专用报错分支须给出通用拒绝链和异常契约。
  拒绝发生得更早或文案更具体，本身不足以证明需要给公共框架添加 op 名单。
- **反例**：通用路径尚未覆盖的独立输入约束、必须阻止副作用的边界检查，或已明确要求的诊断契约，
  需核实后保留在恰当层；不能将所有提前校验或所有按 op 分发的合法处理一概判为冗余。

### PRO-DSL-005：类型注解的表示与消费路径

- **适用条件**：新增或修改 DSL 类型名、类型标注类、表达式 wrapper 或其解析路径。
- **检查内容**：分别追踪注解在 Python 中如何求值、parser 如何构造 IR type，以及 kernel 内的值
  实际由谁持有和消费。若 parser 直接从 AST 生成 IR 类型，后续只使用 IR Expr/type，则不能以
  注解名字需要可访问为理由，另建一套没有运行期消费者的 wrapper、构造模式和对象状态。
  只需支持注解求值时，应复用已有注解设施或保留必要的最小表示；先判断整类必要性，不能仅删除
  其中一个闲置字段或参数。Python 立即求值注解与延迟注解两条合法路径均须考虑。
  同时比较新类型与已有 DSL/IR 类型的语义：若只是在已有类型上增加标记或配置，优先扩展已有
  DSL 类型，使其与 IR 的表达一致；不要另建平行类型、解析分支及配套文档。提出独立类型时须说明
  现有表示无法表达的契约，不能把“新增名字更直观”或 PR 自行新增的说明当作必要性证明。
- **报告证据**：注解入口、AST 到 IR 的映射、实际值的表示与消费方，以及可复用类型的字段/语义。
  无用途 wrapper 与不必要的类型分裂可关联，但应分别说明；与 `PRO-DATA-001`、`PRO-SIMPLE-001`
  同根因合并，不能只报告局部冗余而漏掉整组设计问题。
- **反例**：有真实执行消费者的 Expr 包装、参与运行期 shape 绑定的注解对象，或现有类型无法表达的
  独立语义，可以有专用对象；不机械要求所有 DSL 类型与 IR 类型一一对应。删除冗余类仍须保留
  合法注解的求值能力，不能直接删名字导致函数定义报错，也不能将新类问题扩大为旧类型体系重构。
