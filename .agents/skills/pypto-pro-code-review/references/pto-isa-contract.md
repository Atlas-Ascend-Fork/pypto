# pto-isa 深度契约检查（可选）

## 启用与范围

仅在用户明确开启本专项时读取和执行，默认关闭。它扩展 `PRO-API-001`、`PRO-ERROR-001`
和 `PRO-CODEGEN-001`，检查从 DSL 到 pto-isa 实现的输入契约，不替代基础检视。
范围限于本次改动影响的 op、共享校验/生成 helper 的消费者，以及用户明确指定的接口。
本专项可用测试取证；测试自身的检视按[测试规则](test.md)，不纳入 ISA 契约审计。
不自动修改框架、pto-isa 或发布 PR 评论。

## PRO-ISA-001：前端校验覆盖实际 pto-isa 调用的约束

- **适用条件**：专项已开启，且检视范围内的 DSL/IR op 最终生成 pto-isa 调用；也包括
  校验、类型映射、模板参数、分发条件或依赖版本变化导致该调用可接受的参数组合发生变化。
- **检查内容**：固定最新 `master` 校验基线与目标（用户显式指定其他基线时从其约定），
  追踪最终重载/特化及实现中的全部适用约束，将这些约束
  反推到 DSL 参数和类型，逐项核对前端接受域。重点找出前端接受、经转换后却无法通过
  pto-isa 模板实例化或指令约束的具体组合；不仅比较接口参数个数、名称及独立 dtype 白名单。
  可在前端判断的非法输入应通过有 DSL 源码位置的诊断拒绝，不能只留给 pto-isa/bisheng 报错。
- **报告证据**：框架版本、校验基线 commit、与实际依赖的已知差异、目标架构、DSL 参数组合、
  完整 lowering/生成调用、命中的
  pto-isa 实现及约束位置、已有校验和遗漏位置，以及实际或源码推导的失败类型。
- **反例**：前端或公共类型构造已拒绝；合法 lowering 会完成类型转换、补齐或选择另一重载；
  该特化在目标配置下不可达；某条件仅为设备运行时断言。不能直接用 pto-isa 原始参数域限制
  DSL，或要求前端静态决定运行期未知值；不得通过新增限制排除框架本应支持的合法转换。

## 执行方法

### 1. 获取并固定最新 master 校验基线

默认仓库为 [cann/pto-isa](https://gitcode.com/cann/pto-isa)，Git URL 为
`https://gitcode.com/cann/pto-isa.git`。每次开启深度检查时，从远端获取当时最新的 `master`，
使用新建临时目录保存独立源码快照，不读取本机旧仓作为默认基线，也不切换、拉取或覆盖用户仓。
可用以下方式获取；命令中的目录变量仅用于本次检查：

```bash
PYPTO_ISA_REVIEW_DIR=$(mktemp -d)
git clone --depth 1 --single-branch --branch master \
  https://gitcode.com/cann/pto-isa.git "$PYPTO_ISA_REVIEW_DIR/pto-isa"
git -C "$PYPTO_ISA_REVIEW_DIR/pto-isa" rev-parse HEAD
date -u +'%Y-%m-%dT%H:%M:%SZ'
```

记录获取时间、Git URL、分支、完整 commit SHA 和快照路径；确认下载成功后才继续依赖分析。
同一轮检查的所有 op 使用这一固定 SHA，不在中途跟随 master 更新。下载失败时将专项标为
未完成，说明原因并继续不受影响的基础检视，不能静默回退到旧仓并声称检查了最新 master。
用户显式指定其他仓、路径或版本时才覆盖默认基线，并在报告中写明该约定及实际版本。

另行记录框架 head/base、本次受影响的 op、目标架构以及影响实现选择的宏和编译选项。
沿框架编译配置、依赖声明及实际 include 搜索顺序核对已知的实际依赖版本，区分“校验基线”
与“当前编译依赖”：以下载的 master 为本专项依据，即使实际依赖不同或暂不明确，也可继续
对最新基线做静态契约检查；不能因此默默改用旧依赖，或一概停止该专项。
仅在 master 中出现的约束差异，应表述为相对该基线的兼容性/校验缺口；要声称当前框架已会
发生 bisheng 编译失败，还须证明当前依赖同样具有该约束或提供对应复现。版本差异不能直接
当成本次 PR 引入的功能缺陷。执行编译验证时另记 bisheng/CANN 版本。

### 2. 从生成调用追到实现

按每个受影响 op 的可达分支建立映射：

`DSL 声明/注解 → parser 与 Python IR builder → IR/lowering → backend/codegen → 生成的 C++ 调用 → pto-isa 实现`

记录参数顺序、输出/临时 Tile、隐式转换、默认属性、dtype/shape/layout/memory space 的映射、
显式与推导的模板参数及重载选择条件。一个 DSL op 映射多个指令时分别追踪；共享 helper
改动须检查受影响消费者。内部 IR op 沿实际生产者追踪，不要求为内部调用补造前端 API。

从实际调用符号进入 pto-isa 公共入口，继续追踪宏、转发、架构选择、重载、特化及 `*_IMPL`
和检查 helper，直到约束实际生效的位置；不能停在文档、声明或某个同名函数。
例如 `include/pto/common/pto_instr.hpp` 的 `TADD` 会经分发进入对应架构的实现及 `TAddCheck`；
具体路径及符号以固定的校验基线版本为准，不能机械假定每个 op 都有同名头文件。

### 3. 提取并反推每条适用约束

阅读选中实现及必要的 Tile/GlobalTensor 类型定义、traits 和 helper，提取 `static_assert`、
`enable_if`/concept、`if constexpr` 分支、模板形参要求和底层指令签名等真正生效的条件。
文档用于对照与补充语义，不能代替实现；有矛盾时记录版本和差异，不自行选择更宽或更窄的条件。
核实哪些分支被 `if constexpr` 等编译期机制裁剪；普通运行时 `if` 不会因此免除分支中模板的
实例化约束，不能把运行时不走该分支当作编译可通过的依据。

按实现涉及的维度检查组合关系：

- 输入、输出、临时参数的 dtype 组合及相等/转换关系，而非每个参数分别在白名单内即可。
- 静态 shape、rank、valid shape、布局、分形/打包格式、stride、对齐、容量及 memory space
  之间的关系，区分字节、元素、实际分配形状和有效形状。
- mode、枚举、立即数/常量性、范围、可选参数、模板默认值与特定重载/目标架构的联动限制。

仅检查实际实现具有的约束，不给每个 op 强加上述全部类别。区分编译期硬约束、可由框架
静态推导的条件和仅运行时可知的条件；不能把设备 `PTO_ASSERT` 自动当成 bisheng 编译失败。
被分支保护、已归一化或在其他阶段保证的条件，应写出证明，不直接照抄为新的前端检查。

### 4. 核对拦截位置与反例

逐条沿实际路径检查参数绑定、解析后的 IR type、`ir/_utils.py`、op builder、通用类型构造及
后续变换。记录约束是已被前端拒绝、由合法转换保证、仅在较晚框架阶段拒绝、会落到底层，
还是尚未确定；晚于前端但早于 bisheng 的检查也须单独标注，不能说成已导致编译器报错。
前端错误须使用项目异常机制，并关联 op 调用或具体参数的 DSL span；单靠文档约束、测试中
未出现非法值，或最终捕获 bisheng 的通用异常，都不能证明完成前端拦截。

对候选遗漏构造一组具体值，使它通过已有前端校验并选中该实现，却违反目标约束；同时找一组
相邻合法值，确认建议不会误拦。关系约束要给出违反关系的组合，不能只说“检查不充分”。
结合 base 判断本次引入或扩大的缺口；未变更的历史问题单独注明，不充当本次 PR 新增意见。

建议按 `PRO-ERROR-001` 优先复用 `python/pypto_pro/ir/_utils.py` 的公共接口；缺少时分析并
提炼通用原语，op 组合表达业务关系。不要为此在 Python、C++ 和 codegen 重复堆叠同一校验，
也不要改 pto-isa 或弱化其约束来掩盖框架缺口。只能运行时确定的条件应说明其保证机制或
未覆盖范围，不以强制常量化取消合法动态能力。

### 5. 必要验证与覆盖结论

优先用最小 DSL 片段验证前端接受/拒绝及生成调用；需要确认重载、模板实例化或编译诊断时，
再使用固定基线的头文件、目标宏与记录的编译参数做最小 bisheng 编译验证，并确认 include
实际命中该快照，而非 CANN 或其他目录中的旧头文件；不要为此覆盖已安装依赖。
当前依赖的复现与最新 master 基线的验证分别记录；缺少对应原生产物时，不用其他版本的
解析/生成结果冒充目标行为。此专项不默认要求 NPU 运行或全量构建；编译失败归因
须排除环境缺件、头文件版本错误等原因。静态推导与实际执行分别记录。

在通用覆盖表中为 `PRO-ISA-001` 保留一行，并附逐约束记录：

| DSL op / 路径分支 | pto-isa 基线 commit 与实现位置 | 底层约束及生效条件 | DSL→IR→调用参数映射 | 框架拦截或转换保证的位置 | 反例/合法对照与验证 | 状态/发现 |
|---|---|---|---|---|---|---|
| 按实际调用填写 | 精确到重载、特化或 helper | 每条适用约束单独记录 | 包含隐式和模板参数 | 标明前端、后续阶段或未拦截 | 区分源码推导与执行 | 已核对 / 未完成；关联发现编号 |

只覆盖已识别约束或抽样测试，不能声称“所有非法组合都被拦截”。完成结论须限于所检查的
op、目标、校验基线版本和可达分支；每条适用约束都有依据才可标为已核对。动态条件、未知分支、
依赖或验证缺口单独列出；与基础规则命中的同一根因合并报告，保留各规则编号和源码证据。
