# CCE codegen / backend 检视规则

## 适用范围

IR 到生成代码的转换、op 注册、指令映射及后端约束的改动。
涉及 IR 语义、目标架构选择或源码编译执行时，通过[模块索引](review-checklist.md)
加载 IR、runtime 等相关模块规则。代码结构分析、优化、变换遵循 [Pass 规则](pass.md)。

## 模块专属规则

### PRO-CODEGEN-001：op 声明、实现与返回类型一致

- **适用条件**：新增或修改 op 的后端声明、实现或 IR 到 CCE 的转换。
- **检查内容**：暴露给前端的 op 按公共规则 `PRO-API-001` 核对完整跨层一致性。
  仅供框架内部使用的 IR call op 允许只在后端定义，核对实际构造、调用方与后端声明、实现的
  参数、返回值及语义是否一致，不要求补充前端层。所有 op 均不得漏加或多加参数及返回值；
  无返回值 op 的返回类型必须设为 `NoneType`。
  类型迁移时，对每个修改过的类型推导先核对 op 是否真的产生结果，再判断是否需要适配新类型。
  沿前端声明、IR 使用方式和 backend 返回路径验证；只写入目标对象的副作用不能冒充返回值，
  也不能因旧推导返回了目标类型，就继续为其增加子类返回分支。只报告本次新增或扩大的错误契约，
  不据此审计或修改所有历史 op。
- **报告证据**：具体 op 在其实际适用层之间的契约差异，或无返回值 op 的错误返回类型；
  内部 IR call op 缺少前端公开接口本身不构成违规。

### PRO-CODEGEN-002：pipe 元数据与实际指令流水线一致

- **适用条件**：新增 backend op 注册，或修改生成指令、访存方式、`set_pipe` 及其查询/消费路径。
- **检查内容**：逐个 op 对照注册的 pipe 与生成代码实际执行的指令、访存及标量运算，不能只检查
  参数和返回值。区分 kernel 的 Cube/Vector 执行域与指令的 S/V/MTE 等流水线；在 Vector 域运行
  不等于使用 V pipe。指针结果、描述符解码、标量地址计算和标量读写也须检查，不能因没有 Tile
  参数而跳过；不要复制相邻 op 的 pipe。追踪元数据的查询及同步/调度消费者，按目标依赖源码或
  正式指令语义确认归属；多流水实现按框架已有表达契约核对，不凭名字或结果类型选择 pipe。
- **报告证据**：注册位置、实际生成的指令/表达式、应属流水线及依据。元数据不符本身可作为
  规范违规；若声称同步错误或精度故障，还须给出真实消费链和可触发场景，不能仅从标记错误推断。
- **反例**：返回标量的归约可能实际使用向量指令；指针参数也可能被 DMA 指令消费。
  都不能仅凭参数/返回类型标成 S。仅生成编译期描述信息的 op 按框架约定处理，不虚构硬件指令。

### PRO-CODEGEN-003：类型与值表示迁移后的统一生成路径

- **适用条件**：新增 IR 类型、改变运行时表示，或为类型/表达式生成新增辅助入口、状态及分支。
- **检查内容**：从实际构造入口枚举生成的类型及默认情况，再检查类型转换、声明、表达式求值、
  聚合/控制流复制及 backend 消费是否遵循同一表示约定。仅有类型声明、手工构造的测试或旧实现
  不足以证明需要保留两套生产路径；有明确外部契约的基础类型入口则须保留其语义。
  先对照已确认的迁移约定核实源头类型，尤其区分“没有附加数据的业务值”和“迁移前的基础 IR
  类型”。若前者已统一表示为新类型的零数量情况，不能用后端对旧类型的补偿包装反证宽泛匹配
  或兼容回退必要；应同时检视源头表示、生成类型映射与解包条件是否符合约定。
  检查以下三个方面，不能只确认生成代码可以编译：
  1. **类型转换**：先查既有通用入口与类型转换器。新增类型应在既有转换职责中接入；核对是否在
     多个调用方重复决定包装类型、零数量特例或旧类型兼容分支。默认参数已覆盖普通情况时，
     不应为区分新旧表示继续维护无独立需要的开关和回退。类型名查询引入状态写入也须说明必要性。
     当真实生产路径已统一为新 IR 类型，且没有保留旧类型的独立入口契约时，旧类型的默认值、
     补包装或兼容分支应按冗余实现报告。零数量是新类型字段的合法值，不应由类型转换失败
     兜底得到。修复应收敛到新类型的不变量，不默认用新增拒绝分支或第二套运行时校验替代旧兜底。
  2. **值与投影**：在同一生成上下文中，表达式入口应返回该 IR 值的完整运行时表示，赋值、tuple
     和控制流传递复用该语义。backend 需要内部成员或指针时，在明确的操作数适配边界取出；
     不应隐式改变通用入口的含义，再让公共遍历逐处选择另一套“完整值”入口作为补偿。
     若两个接口返回值确有区别，继续追查区别是否由不合理的职责拆分制造，不能止于“二者不等价”。
     按调用边界区分表示，而非按源文件名或函数类别判断：SIMT/SIMD 调用者仍可能持有完整 tile，
     被调用函数内部才是指针 ABI。已存在统一操作数投影入口时，逐处比对新增手工成员访问是否
     具有同一语义；调用点自行拼接 `.tile` 不因位于 SIMT 文件就成为必要例外。
  3. **对象初始化**：按一个完整对象核对类型、构造参数、地址及附加运行时字段的初始化负责者，
     对照其发射位置和依赖值何时可用。不能只把新字段放进 op 回调、其余留在公共预扫描，
     就认定初始化已经归入 op。优先扩展原有完整初始化入口；原职责不适合时整体收敛到负责的
     op 实现。必要的声明提升与运行时初始化可以分阶段，但不能因此分散对象语义的维护。
     对构造参数先追踪实际生产者保证，区分类型中的静态值/动态哨兵与对象运行时字段。
     若类型字段只会是常量或缺省值，不为运行时字段的可变性保留该类型字段的任意 Expr 分支。
     核对模板实参与构造参数共同决定的初始化契约，包括逐维静态/动态混合的情况；静态值
     已由模板表达时，不默认再传一次构造参数。为具体疑点核对依赖构造签名即可，无须开启整套
     pto-isa 深度审计，也不为删分支擅自收紧已有独立 IR 入口的合法输入。
- **报告证据**：实际生产者、类型/值映射、旧分支的可达性，以及重复决策或职责拆分的位置。
  初始化问题须说明各字段及执行点；统一建议须覆盖完整值复制和底层操作数使用，不能只替换函数名。
- **反例**：成员访问不是完整对象赋值；SIMT/VF 的指针 ABI 与普通 tile 描述符可能具有真实差异，
  不能因为共享一个 IR 基类就强行统一。类型转换器内部复用底层类型拼装本身不构成双路径；
  已有的通用类型接口也不会因为新增子类而自动变成冗余接口。
  只读取继承字段的 helper 接受基类，以及内部生成底层 PTO tile 类型，不等于支持旧的运行时
  值表示；不能为清理旧类型兜底而机械替换全部基类参数或删除底层类型拼装能力。

tuple 类型比较遵循公共规则 `PRO-TUPLE-001`：结构相等不能替代类别信息比较。
新增暴露给前端的 op 还须加载 [DSL/parser 规则](dsl-parser.md)，检查参数解析与 `@op_impl` 注册。
