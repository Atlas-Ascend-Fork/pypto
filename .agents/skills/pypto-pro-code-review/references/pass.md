# Pass 检视规则

## 适用范围

源码或 IR 的代码结构分析、优化、转换，以及 Pass 的实现和接入。
按功能职责选择本模块，不能因实现位于 parser、codegen 或 runtime 目录就跳过。
parser 构建 IR 所依赖的必要处理边界见[通用清单的模块职责](review-checklist.md)。

## 模块专属规则

### PRO-PASS-001：基于框架 Pass 体系实现分析与变换

- **适用条件**：新增源码或 IR 的分析、优化、转换功能，或新增、修改 Pass 实现。
- **检查内容**：功能应实现为 Pass，基于框架 Pass 基类体系构造或继承其实现基类，
  不另写一个任意类来替代 Pass 做 IR 转换。核实该功能在框架流程中的接入位置和调用方式。
  当前框架的 `CreateFunctionPass`、`CreateProgramPass` 工厂以及 `PassImpl` 实现类都是
  基于 Pass 体系的接入方式，不要求每个 Pass 都另建派生类。
  默认按变换粒度选择 Function/Program 工厂；需要自定义状态时再使用 `PassImpl` 实现类。
  从实际生产者和前置变换确定 Pass 接收的节点、表示及不变量，逐一核对新增分支的可达性；
  基础 IR 能表达某种形式，不等于当前流水需要兼容它。有明确独立入口契约时分别记录。
- **报告证据**：该功能承担的分析或变换职责、实际实现与调用路径，以及绕过 Pass 体系的位置。
  Pass 内部使用 visitor、mutator 或辅助函数不等于绕过 Pass；应检查对外的功能入口。

### PRO-PASS-002：分析结果的完成与查询边界

- **适用条件**：Pass 构建分析结果表，或提供查询接口供后续变换消费。
- **检查内容**：沿以下生命周期检查，不能仅凭已有 visitor 和结果表认定完成了解耦。
  1. **生产与覆盖**：明确分析入口、更新者及结果域。查询接口若接收一般表达式，检查分析
     是否覆盖消费者会传入的各类表达式，不能以只记录变量证明覆盖完整。
  2. **稳定与传播**：核对依赖更新、循环回边、循环变量之间的传递和嵌套合流，明确结果何时
     可被消费。保留既有控制流语义，不能为实现一次遍历漏掉传播，也不预设求解算法。
     列明每类边的属主、目标与来源的对应关系及占位值含义；区分单一来源传递、投影和多来源
     汇合，检查覆盖、并集等更新方式是否表达了相应职责。复用计算原语不应抹去这些语义边界。
  3. **查询与消费**：约定查询已完成分析时，查询应读取结果；缺项后重新递归推导、执行传递
     规则或控制流求解，应检查是否属于分析阶段未完成的工作。将求解藏进私有 helper 不消除
     耦合。合法按需分析须明确其契约，不能用按需命名掩盖原有完成保证的变化。
  4. **有效期**：核对依赖或 IR 改变后结果的更新、失效或重建边界，不能把中间值或旧缓存
     当成最终结果。接口解耦、遍历次数和实际成本分别判断。
- **报告证据**：分析入口、写表节点范围、查询契约、未完成的传递逻辑与实际消费者，以及
  结果稳定和失效的时机。重复计算须给出实际命中路径；性能结论另需测量或复杂度依据。
  对不同传递语义共用实现的问题，区分职责表达与结果错误；当前 SSA、单调性等条件下若结果
  等价，应如实说明，不能以更清晰的拆分方案反推原实现必然算错。
- **反例**：契约明确的按需分析，或从稳定结果计算轻量派生值，无需预计算所有节点；
  统一分析阶段可以有内部迭代。不能从“查询应解耦”推导出必须一次线性遍历或引入新依赖图。

涉及基础 IR 节点或类型变化时继续读取 [IR 规则](ir.md)；模块独立性遵循公共规则 `PRO-MODULE-001`。
