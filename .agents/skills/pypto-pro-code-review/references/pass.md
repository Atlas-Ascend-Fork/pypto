# Pass 检视规则

## 适用范围

源码或 IR 的代码结构分析、优化、转换，以及 Pass 的实现和接入。
按功能职责选择本模块，不能因实现位于 parser、codegen 或 runtime 目录就跳过。
parser 构建 IR 所依赖的必要处理边界见[通用清单的模块职责](review-checklist.md)。

- [Pass、PassImpl 与工厂接口](../../../../framework/include/ir/transforms/passes.h)

这些入口用于理解和查证框架接口，不表示现有分析或转换实现均符合用户规则。

## 模块专属规则

### PRO-PASS-001：基于框架 Pass 体系实现分析与变换

- **适用条件**：新增源码或 IR 的分析、优化、转换功能，或新增、修改 Pass 实现。
- **检查内容**：功能应实现为 Pass，基于框架 Pass 基类体系构造或继承其实现基类，
  不另写一个任意类来替代 Pass 做 IR 转换。核实该功能在框架流程中的接入位置和调用方式。
  当前框架的 `CreateFunctionPass`、`CreateProgramPass` 工厂以及 `PassImpl` 实现类都是
  基于 Pass 体系的接入方式，不要求每个 Pass 都另建派生类。
  默认按变换粒度选择 Function/Program 工厂；需要自定义状态时再使用 `PassImpl` 实现类。
  从实际生产者和前置变换确定 Pass 接收的节点、表示及不变量，逐一核对新增分支的可达性；
  基础 IR 能表达某种形式，不等于当前流水需要兼容它。有明确独立入口契约时分别记录。
  实现归属与调用编排分别检查：沿实际编译入口列出已有 Pass 的执行位置和顺序，新增独立
  IR Pass 应接入同一编排入口。PyPTO Pro 的通用 Pass 由 Python 编译流程统一调用，不能
  因实现和 binding 都在 C++，就在代码生成器的入口中隐式执行。核对同步、插桩和后端消费
  的先后依赖，以及直接调用 codegen 的测试是否需要先显式运行 Pass。
- **报告证据**：该功能承担的分析或变换职责、实际实现与调用路径，以及绕过 Pass 体系的位置。
  Pass 内部使用 visitor、mutator 或辅助函数不等于绕过 Pass；应检查对外的功能入口。
  编排问题给出统一流程、隐藏调用点及其独立阶段语义；使用了 Pass 工厂不能单独证明接入正确。
- **反例**：有独立契约的后端内部表达式归一化不自动等同于通用 IR 优化阶段；核实其输入域和
  职责后分别判断。不借新增 Pass 的检视迁移全部历史后端处理，也不保留两处调用作为兼容补丁。

### PRO-PASS-002：分析结果的完成与查询边界

- **适用条件**：Pass 构建分析结果表，或提供查询接口供后续变换消费。
- **检查内容**：沿以下生命周期检查，不能仅凭已有 visitor 和结果表认定完成了解耦。
  1. **生产与覆盖**：明确分析入口、更新者及结果域。查询接口若接收一般表达式，检查分析
     是否覆盖消费者会传入的各类表达式，不能以只记录变量证明覆盖完整。
  2. **稳定与传播**：核对依赖更新、循环回边、循环变量之间的传递和嵌套合流，明确结果何时
     可被消费。保留既有控制流语义，不能为实现一次遍历漏掉传播，也不预设求解算法。
     列明每类边的属主、目标与来源的对应关系及占位值含义；区分单一来源传递、投影和多来源
     汇合，检查覆盖、并集等更新方式是否表达了相应职责。复用计算原语不应抹去这些语义边界。
  3. **查询与消费**：约定查询已完成分析时，查询应读取结果；缺项后重新递归推导、执行传递
     规则或控制流求解，应检查是否属于分析阶段未完成的工作。将求解藏进私有 helper 不消除
     耦合。合法按需分析须明确其契约，不能用按需命名掩盖原有完成保证的变化。
  4. **有效期**：核对依赖或 IR 改变后结果的更新、失效或重建边界，不能把中间值或旧缓存
     当成最终结果。接口解耦、遍历次数和实际成本分别判断。
- **报告证据**：分析入口、写表节点范围、查询契约、未完成的传递逻辑与实际消费者，以及
  结果稳定和失效的时机。重复计算须给出实际命中路径；性能结论另需测量或复杂度依据。
  对不同传递语义共用实现的问题，区分职责表达与结果错误；当前 SSA、单调性等条件下若结果
  等价，应如实说明，不能以更清晰的拆分方案反推原实现必然算错。
- **反例**：契约明确的按需分析，或从稳定结果计算轻量派生值，无需预计算所有节点；
  统一分析阶段可以有内部迭代。不能从“查询应解耦”推导出必须一次线性遍历或引入新依赖图。

### PRO-PASS-003：变换实现的必要性与既有框架复用

- **适用条件**：新增或修改 Pass 的遍历、节点重建、校验、辅助接口及临时状态。
- **检查内容**：沿实际输入生产者、框架变换入口和输出消费者逐项核对，不能以“属于 Pass”
  或“用了 visitor/mutator”证明内部实现必要。
  1. **变换粒度与重建**：完整读取工厂及基类对应实现，比较已有节点递归、未变化节点复用、
     函数/Program 重建及字段保留能力。逐项确认自写遍历、changed 标记、容器复制、构造转发
     是否提供额外语义；仅为自加校验而扩大变换粒度时，先证明该校验必要。
     区分语义不变与指针身份不变：只有实际消费者或既有契约需要后者时，才据此保留额外状态。
     基类已提供的复用无需删除，但不能为复刻它另写一套遍历。比较工厂时同时核对元数据保留，
     不能为了减少代码丢失原有语义，也不能用为新增优化自写的测试反证该优化必须存在。
     一处工厂缺少能力只排除该工厂；继续核对 visitor/mutator 的同粒度入口，不能据此豁免
     自写的外层遍历、重建及状态。把模式筛选和本 Pass 的改写留在适当 override 中进行比较。
  2. **校验归属与可达输入**：列出新增校验的谓词、真实入口和已有保证，追踪 parser、实例化、
     op 构造及前置 Pass 是否已确保它。被原生 API 暴露、基础 IR 能构造、测试可手工生成都
     不能单独证明需要重复检查；有独立受支持输入契约时核实未覆盖约束。不要混淆输入校验
     与内部结果检查；内部策略注册本身不构成独立阶段边界，自身转换完成后的重复遍历按
     PRO-SIMPLE-001 判断。
     签名、调用关系、操作作用域和变换支持范围分别核对；找到其中一类重复检查，不能替代
     其余谓词的职责判断。前端尚未拦截某种操作，也不能自动证明应由变换 Pass 补做语言校验。
     将“读取变换需要的数据”与“验证数据合法”分开核对：一个取值 helper 中的检查不能因为
     返回值有消费者就整组保留。按 PRO-MODULE-001 固定本次职责与可依赖契约，区分已有
     输入保证、本次改写产生的不变量和只能在当前阶段判定的条件；据此决定检查的负责者，
     不因相邻模块有缺口就默认由 Pass 补齐，也不以删除重复检查为由改变支持输入域。
     删除分类分支前列出真实可达的调用种类，并比较注册表/模式匹配加默认递归能否覆盖它们。
     辅助函数调用、元数据查询等无需变换的节点，不构成必须保留命名空间分流的理由；
     匹配未命中也不自动意味着输入非法。前端负责合法性时，优先检查默认遍历是否保持原语义，
     不要求 Pass 重复校验；规则自身的变换前提与明确独立的校验契约仍逐项核实。
  3. **辅助层与临时状态**：比较现有 builder、mutator、命名与类型工具的完整语义，再判断
     新 helper、包装层、结果表、名称集合及缓存的必要性。异常恢复要追踪对象寿命和恢复后的
     实际使用；异常使本次变换退出且局部对象销毁，不能仅为复原不再使用的临时状态增加逻辑。
     比较粒度包括可独立复用的构建原语，如插入点、语句累积、节点构造；现有工具不能替代
     整个上下文，不代表这些子操作也需要重新实现。保留确有额外语义的部分，并说明组合边界。
     对块栈、回调和作用域包装列出真实嵌套调用及状态消费者；仅用于暂存语句或取得源码位置时，
     比较直接使用 builder/插入点与显式 span 的方式。接口放入 context 须有共享状态或生命周期
     依据，不能只因调用方位于该 Pass 就把通用节点构造变成 context 的职责。
  4. **实际成本与局部必要性**：记录每次遍历、递归和状态读写的独立目的。能在已有访问中完成
     且无顺序依赖的同义处理应复用；分析稳定、跨函数关系等真实依赖可以需要独立阶段。
     功能上等价的重复实现也可构成规范问题，但不得没有测量或复杂度依据就声称性能下降。
  5. **表达式路径与取值职责**：追踪同一逻辑量从 IR 输入、临时表示到最终表达式的完整过程。
     先核实消费者或已确认方案是否要求当前阶段输出常量节点；仅需要相同数学结果时，比较
     统一构造表达式与分别手算常量、构造动态表达式两条路径。构造器本身不做常量折叠，
     不能单独证明双路径必要；后续简化或编译是否已经完成该工作也须核实。明确要求本阶段
     常量化时保留该契约，不能用未验证的替代或削弱断言冒充简化。取值逻辑若散在预扫描、
     可选值记录、闭包捕获与消费点中，核对能否以源对象和必要索引为输入，直接返回语义完整
     的表达式；不能把依赖某个固定操作数的闭包当成已完成的公共取值能力。
     静态值与运行时查询的选择可以封装在取值边界，但不应让下游再次区分同一事实。校验归属与取值是否完整封装是不同问题，移动校验不能代替后者的核对。
  6. **信息来源与表示必要性**：从变换的输出语义反推所需数据，确认每项事实的权威来源和
     已有关系保证。契约已确定的信息不应通过扫描其他对象、建立旁表或再次比较来重建；
     确实依赖多方信息的变换则保留所需分析，不能机械改成只读一个来源。
     将新增字段、描述符和哨兵与输入类型已有的概念逐项对照：它是否表达本次支持域中的
     独立自由度，还是重复编码已有类型、可直接导出的属性，或为未要求的更一般场景建模。
     分别回答“计算是否需要这项事实”和“是否需要新增这种表示”：给出字段的赋值来源、
     消费方式及直接使用原有信息的替代路径。证明计算正确或事实必要，不能代替后一项判断。
     后者应比较直接使用现有表示的方案；真实的布局、别名、生命周期等差异不能被简化抹去。
     区分语义范围与存储寻址等不同事实，在需要转换的边界处理，不能为删除冗余表示而混淆
     两者或缩小原有支持域。
- **报告证据**：新增实现及其完整调用链、已有公共能力或上游保证、缺少独立语义的具体部分，
  以及删除/复用后仍满足原契约的原因。校验与状态必须逐项分析，不能因为一部分必要保留整组。
- **反例**：跨函数重写、明确独立的输入或调试契约、必须先完成的分析、可恢复重试、共享对象
  的异常安全，以及现有工具无法表达的变换均可能需要专用逻辑。公开接口兼容性和已授权扩展
  能力要保留；不把所有 helper、内部断言、多次遍历或注册设施一概判为冗余。
  常量专用算法若有不同的溢出、精度或生成代码要求，不能机械合并；先核实公共构造器的折叠
  行为。必要的运行时元数据查询、语义性块作用域和跨节点分析也不能仅因存在 builder 就删除。

涉及基础 IR 节点或类型变化时继续读取 [IR 规则](ir.md)；模块独立性遵循公共规则 `PRO-MODULE-001`。
