# PyPTO Pro 模块索引与通用检视清单

## 使用方式

本文件维护模块索引、通用及跨模块规则；模块专属规则分别维护在下列文件中。
用户规则来自本次提供的 `review.md`，已整理到本技能中，使用时不依赖该输入文件。
各条“用户依据”保留原条目编号以便追溯。已有代码不符合规则，不构成规则的例外。
本清单及其索引的模块规则仅适用于框架逻辑代码，不检视 UT/ST 及仅供测试使用的辅助代码。
测试源码和执行结果仅作为框架行为的验证依据，不对测试自身套用规则或产生检视意见；
测试专属检视规则待用户另行补充。排除的测试改动在范围说明中列明，不计为规则覆盖缺口。
按改动目录和实际影响关系选择阅读范围，不意味着每个 PR 都要检查所有模块。
例如 parser 改动若影响 IR 语义及其消费方，应继续读取 IR、Pass 和相关 codegen/runtime 规则。
按用户规则判定是否违规，并核实目标版本中的实现、调用方、测试及正式文档以形成证据，
不能仅凭关键字命中判定缺陷。下列源码链接是阅读入口，不代表其中的现有实现均符合规则。

## 规则覆盖记录

每次检视必须建立并随检查更新下表，最终报告中保留。依据实际读取的规则标题生成条目，
全部通用规则及所加载模块的每条规则各占一行，不能只列命中问题的规则。
同时列出本次加载的模块规则文件，以及模块索引中其余模块不适用的原因。

| 规则编号（链接原文） | 适用的改动文件 / 符号 | 检查状态 | 证据与结论 |
|---|---|---|---|
| 按实际规则填写 | 覆盖该规则的全部适用改动 | 已核对 / 不适用 / 未完成 | 代码位置、判断依据及关联发现编号 |

- **已核对**：已检查该规则的全部适用改动及检查内容。写明相关代码位置和判断依据，
  列出所有已确认违规对应的发现编号；没有违规时说明为何符合规则，不能只填“通过”。
  已在 PR 中报告的同一问题关联原评论，不重复提交，也不能记作“未发现违规”。
- **不适用**：说明本次改动为何不满足规则的适用条件，不能用“未发现功能问题”或“测试通过”代替。
- **未完成**：列出尚未覆盖的文件、符号、规则检查项或未决候选问题及原因。
  部分位置已检查或已发现违规，但其他适用位置尚未检查时，仍标为未完成并保留已有证据。

覆盖记录必须来自实际代码检查，不能先填结论再补理由。发现问题不等于该规则检查完成；
同一规则的其他适用位置仍须核对。功能分析与规则检视共用证据，但不能互相替代。
必要性检查须列出新增设施的实际功能入口、最终消费者或外部交付依据，并区分定义、导出、
内部转发、测试及文档引用。不能用“helper 已复用”“参数已消费”或“全部文件已检查”代替这些证据；
用途尚未查清时记为未完成，不用补齐类型桩、文档等配套建议跳过必要性判断。

## 模块索引

| 改动涉及 | 规则文件 | 加载条件 |
|---|---|---|
| DSL / parser | [dsl-parser.md](dsl-parser.md) | 涉及用户语法、解析、作用域或从 DSL 构建 IR |
| Python IR / 原生 IR | [ir.md](ir.md) | 涉及 IR 节点、类型、构造或语义约定 |
| Pass | [pass.md](pass.md) | 涉及源码或 IR 的分析、优化、变换，以及 Pass 实现或接入 |
| CCE codegen / backend | [codegen-backend.md](codegen-backend.md) | 涉及 IR 到生成代码的转换、op 注册或后端指令约束 |
| JIT / runtime | [runtime.md](runtime.md) | 涉及 JIT、源码组装、编译配置、缓存或 kernel 执行 |

跨层 API 改动（`python/src/bindings/ir/`、`python/src/bindings/pypto_pro/`、
`python/pypto/pypto_impl/*.pyi` 等）结合下方通用规则及所暴露接口所属模块的规则检视。
UT/ST 改动不触发模块规则加载；仅包含 UT/ST 的改动不适用本技能。
新增暴露给前端的 op 同时读取 DSL/parser 和 codegen/backend 规则；仅供框架内部使用的
IR call op 读取 codegen/backend 及实际构造、调用路径涉及的模块规则，不要求存在前端解析。
新增分析或变换功能即使位于 parser、runtime 等目录，也要读取 Pass 规则，检查模块归属。

## 模块职责

以下职责来自用户“通用 5.1–5.5”，用于判断功能应放在哪一层。

| 模块 | 职责与边界 |
|---|---|
| DSL / parser | 源码到 IR 的转换；仅保留构建 IR 所依赖的必要优化和 lowering，例如 SSA、常量折叠、函数展开 |
| IR | 描述程序结构的通用数据结构；非必要不新增或修改基础 expr、stmt、type，特定功能优先用 call op 表达 |
| Pass | 代码结构的分析、优化、转换 |
| Codegen / backend | op 的后端声明与实现，以及 IR 到 CCE 代码的转换 |
| JIT / runtime | JIT 和二进制场景的编译、运行时逻辑，以及整个框架流程的调用串联 |

## 通用及跨模块规则

以下规则保留各自的适用条件，不因加载本文件就要求每项均适用于当前改动。

### PRO-API-001：op 与公开 API 的跨层一致性

- **适用条件**：新增或修改暴露给前端的 op，或公开 IR/codegen API 的签名、返回类型、公开语义发生变化。
- **检查内容**：先根据接口暴露情况和实际构造、调用路径区分前端公开 op 与内部 IR call op。
  新增 API 先按 `PRO-SIMPLE-001` 核实交付需要，再检查跨层一致性；被公开导出不等于有必要新增。
  若确认整组接口冗余，优先建议删除该组新增内容；配套缺失可记录，但不能只建议补齐而继续扩大冗余。
  暴露给前端的 op，其文档、API 原型、parser 处理、IR 契约、codegen 声明与具体实现必须完全一致，
  逐项核对参数、返回值及语义，不得漏加或多加；原生公开 API 同时检查 C++ 声明与实现、
  pybind binding、类型桩及 Python 封装。无返回值 op 的类型要求见 codegen/backend 规则。
  对新增前端公开 op，先在目标版本的正式 API 文档及目录入口中确认对应说明是否存在、可达，
  再核对内容；即使 diff 未修改 docs 也不能跳过。源码 docstring 不自动替代正式文档，
  除非已确认文档构建会将其收录并提供公开入口。缺失文档与已有文档内容错误分别记录。
  文档还须核对信息归属：通用类型或控制流约束不应作为单个 API 的专属限制；内部表示变化
  不自动产生新增用户文档的要求。先确认是否影响该 API 的用户用法，再决定保留、迁移或删除说明。
- **报告证据**：前端或公开接口的暴露依据、具体跨层不一致，以及受影响的调用、类型契约或运行结果。
  文档缺失须说明检索的正式文档范围、目录入口及 docstring 是否被正式收录，不能只凭 diff 没有文档文件。
- **反例**：仅供框架内部使用的 IR call op（例如由 Pass 或 lowering 直接构造的内部操作）
  可以只在后端定义，无须补充前端公开文档、API、parser 或 `@op_impl` 注册；
  其实际构造、调用方与后端的契约按 `PRO-CODEGEN-001` 核对。不能仅凭缺少前端层判为违规，
  也不能仅凭缺少前端层就认定其用途仅限内部。内部重构且公开接口不变时，不要求机械修改所有层。
  原生接口明确不向 Python 暴露时，不要求补充 Python binding、类型桩或封装。
- **源码入口**：[codegen binding](../../../../python/src/bindings/pypto_pro/codegen.cpp)、
  [codegen 类型桩](../../../../python/pypto/pypto_impl/codegen.pyi)、
  [Pro API 文档](../../../../docs/zh/api/pro_api/)，以及本次改动 API 的声明、实现和调用方。
- **用户依据**：通用 1.1；codegen 1；用户补充的前端公开 op 与内部 IR call op 边界。

### PRO-ERROR-001：输入校验与异常契约

- **适用条件**：新增 op，或调整 IR 构造、参数检查及错误处理。
- **检查内容**：op 各参数都需要校验；暴露给前端的 op 优先在 parser 完成，内部 IR call op
  按实际构造、调用边界核对，不要求为校验新增前端层。校验逻辑尽量集中，
  复用已有校验接口，将重复且可复用的校验抽取为 `require_xxx` 接口，避免分散、重复和过度防御。
  检查非法输入是否在适当边界被检查；异常类型、错误码及包装后的行为是否符合目标版本的
  异常定义、调用方捕获方式和测试断言。区分输入错误与内部不变量，不规定必须使用某组宏或异常名。
- **报告证据**：能触发该路径的输入、既有校验边界、预期异常契约及改动后的具体偏差。
- **反例**：上游已完整验证；异常实现方式变化但对外契约保持一致；仅因宏名不同不能判定缺陷。
- **源码入口**：[异常定义](../../../../python/pypto_pro/_errors.py)、
  [parser 参数解析与校验](../../../../python/pypto_pro/language/parser/_call_parser.py)、
  [错误处理测试](../../../../python/tests/ut/pypto_pro/ir/op/test_scale_error_handling.py)。
- **用户依据**：通用 1.2–1.4。

### PRO-MODULE-001：模块独立性与职责边界

- **适用条件**：新增功能或调整功能在框架中的位置及交互方式，包括向既有模块、函数添加分支。
- **检查内容**：明确功能在框架流程中的位置、输入输出及交互点；模块内部逻辑应独立，
  避免与框架强耦合或散弹式修改。按上方模块职责检查归属；源码分析和变换功能应实现为 Pass，
  具体遵循 [Pass 规则](pass.md)，parser 仅保留构建 IR 所依赖的必要处理。
  Codegen 与 backend 还须区分内部职责：单个 call op 的参数解释、后端约束校验与指令生成放在该 op
  的 backend 实现；公共 codegen 提供遍历、命名、类型转换、输出及必要的通用上下文。
  从新增公共方法及状态追踪实际消费者；不能用 backend 回调调用公共 codegen 中的 op 专用
  实现，就认定职责已归入 backend。共享设施不因当前只有一个消费者就自动构成违规。
  同一模块内部也要按职责检查：先找已有功能的负责函数，再追踪新增策略由谁决定、结果由谁消费。
  流程编排函数应调用相应功能入口；不能仅因几处修改都在同一模块，就认可在编排层拆解策略、
  计算下层实现细节并零散传参。JIT 的源码组装与编译配置边界见 [runtime 规则](runtime.md)。
  新增 kernel 特性须先按生成产物确定职责：影响 `kernel.cpp` 的部分应在 codegen 内完成闭环，
  并保证生成代码与 global entry 兼容，不能依赖 runtime 事后重写 kernel 源码或在入口补偿其内部差异。
  仅影响 `call_kernel.cpp` 的特性，由 caller 生成逻辑按特性完成拼装，并由后续编译阶段决定
  生成 so 所需的特性 cflag；两种产物都受影响时分别落实上述职责，通过必要的特性元数据衔接。
  在认可新增参数或多套入口适配前，先核对已有兼容接口能否屏蔽执行环境差异；例如 SuperKernel
  的 block idx/num 获取差异可由兼容接口统一时，应优先在生成代码中使用该接口，不能将当前
  改写方案所需的参数传递，直接当作这种改写不可避免的证据。接口适用性按目标依赖版本核实。
- **报告证据**：具体职责错位、内部逻辑泄露到哪些框架位置、重复交互点及应归属的模块。
  新增前端 op 必需的 API/parser/codegen 联动本身不等于散弹式修改，应指出可避免的逻辑分散。
  kernel 特性须列明影响的生成产物、已有兼容接口及其适用条件，说明可避免的跨层适配。
- **用户依据**：通用 2.1–2.2、5.1–5.5；用户对 PR 7036 的 codegen 闭环、global entry 兼容
  及 caller 拼装与特性 cflag 职责的补充约定。

### PRO-FUNCTION-001：函数复用与参数必要性

- **适用条件**：新增功能函数或调整函数入参。
- **检查内容**：考虑函数的复用性与独立性，检查是否与已有函数功能重复。
  helper 被多处复用只证明局部复用关系；其所属功能是否有实际需要仍按 `PRO-SIMPLE-001` 核对。
  逐个核实入参的必要性和实际含义，参数应承载模块或函数间需要传递的数据，避免盲目重复提取入参。
  对共同控制一个功能的开关与配置，列出启用、关闭、默认及非默认配置的行为，核实它们是否具有
  独立语义；被消费不等于必须独立传入。关注关闭功能时配置被忽略或仍泄露到其他行为的组合。
  若配置仅在启用时有意义，评估用一个可选配置表达该状态，减少无意义组合；合并时须保留合法值，
  例如能力掩码 `0` 可能表示已启用但未设置能力位，不能未经核实就把它当作关闭哨兵。
- **报告证据**：可复用的已有函数及其语义对比，或具体多余参数、重复提取路径和实际使用情况。
  耦合参数须给出组合行为、独立配置的必要性或缺失依据，区分已确认的状态设计问题与合并建议。
  不能仅凭函数名称相似判定重复，也不能仅凭参数个数判定接口应合并。
- **反例**：开关用于暂时停用功能并保留有明确用途的预设配置，或参数确有独立消费者和语义，
  可以分别存在；不能把所有“开关 + 配置”都判为冗余。
- **用户依据**：通用 3.1–3.2。

### PRO-DATA-001：数据结构的必要性与复用

- **适用条件**：新增数据结构。
- **检查内容**：说明其表达的数据和存在的必要性，检查是否与已有数据结构重复；
  涉及基础 IR expr、stmt、type 时还须读取 [IR 规则](ir.md)。
- **报告证据**：已有结构与新增结构的字段、语义及使用方对比，或新增结构缺乏必要性的具体依据。
- **用户依据**：通用 4.1–4.2。

### PRO-SIMPLE-001：改动必要性与实现简洁性

- **适用条件**：所有本次新增或修改的代码逻辑。
- **检查内容**：禁止过度防御，杜绝冗余代码、重复实现和散弹式实现，保持逻辑简洁。
  对照本次目标和已确认方案，分别检查可独立保留或撤销的改动；复合条件检查到各子条件，
  相邻分支分别核对。说明每处修改承担的适配职责，不能因其中一处需要修改就认可整段改写。
  对新增接口、observer/hook、版本标记及其 helper，在目标版本中检索调用、别名和注册路径，
  追踪实际功能入口如何启用它、其结果由谁使用。可选回调须找到实际传入的非空回调及用途；
  公开 binding 须继续追踪导出后的消费方，不能把“已绑定”当成用途。
  将互相调用的新增代码作为整体检查：撤销该组代码是否影响本次应交付的行为？只在组内互相引用，
  或只有为该接口新增的 UT、文档示例与版本探针，不能证明本次有必要引入它。
  若没有实际消费者，也没有明确的外部交付需求，按冗余修改报告；不要自行假设未来工具会使用。
  检查新增报错分支时，核对既有通用路径对同一非法输入的处理；若仅按特例重复拒绝且不承担独立约束，
  应复用通用机制。op 分发中的具体检查见 `PRO-DSL-004`，不能只确认“能够报错”就判定必要。
  对方案影响之外的判断保留其原有语义边界；尤其区分精确类型匹配与包含子类的匹配，
  不能仅凭当前类型集合下结果相同，就将两种判断当作同一语义。检查所用接口是否改变了
  类型扩展后的适用范围或校验职责，避免把新的适配义务带入本次未涉及的分支。
  风格统一允许用于本次相关改动中明确需要一致、且职责及语义相同的写法；核对一致性需求
  和等价依据。不能要求所有相邻判断使用同一形式，也不能把所有语义等价的统一调整都报为多改。
  对“变换后再次扫描或校验”的生产逻辑，逐项比对输入来源、上游保证、变换后置条件与校验谓词：
  仅为验证内部实现是否完成自身工作而重复分析、且没有新增约束的部分，属于冗余防御候选，
  应考虑由变换本身保证并用测试验证。另行识别变换未覆盖的合法输入、外部输入边界和独立约束；
  这些检查不能随重复部分一并删除，必要时移到负责该约束的分析或变换阶段。
  参数校验、模块边界、函数及数据结构复用分别按上述规则定位，避免同一问题重复报多条意见。
- **报告证据**：被契约或上游保证排除的防御分支、已有等价实现、无实际用途的逻辑，
  或同一功能无必要地散落多处的具体位置；不能只写“代码不够简洁”。范围问题需指出具体
  子改动、原有语义、本次适配要求，以及保留原实现为何仍满足方案。已确认的无关改动可作为
  规范违规报告，不必虚构运行时故障；语义或授权边界不明确时保留为待确认项。
  无用途问题须给出目标版本、检索范围、引用分类及整组代码与交付目标的关系；全局无字面命中本身
  不足以排除动态注册或外部调用。重复报错须给出特例分支与通用拒绝路径，而非只比较错误文本。
- **反例**：已授权的统一重构、必要的接口迁移，以及有明确一致性需求且不改变原有语义的
  风格调整，不因局部可以回退就被判为多改。有明确独立契约的 IR verifier、跨 Pass 不变量检查、
  外部输入校验或调试断言，不因位于处理之后就自动构成过度防御。
  明确要求交付给外部用户的公开 API、已接入真实工具的诊断扩展点，以及有证据的动态调用，
  不因仓内缺少直接调用而自动判为冗余；同一 PR 自行补充导出、测试和接口说明不自动构成交付依据。
- **案例**：新增 Tile 子类时，将 Tile 的精确 kind 判断改为基类匹配是必要适配；同一条件中的
  Tensor 判断没有这项适配需求，应保留精确匹配。不能仅为两侧都使用 `As<T>()` 而一并修改。
  [PR 6992](https://gitcode.com/cann/pypto/pull/6992/)（head `f9e6350fc653730e210f60d9b9f426f2f2f448a4`）
  的 `parse_target_program(observer=...)` 与 `get_attributes`/`attributes_api_version` 只有测试、
  文档及自身配套引用，实际 JIT 调用不传 observer，属性读取也未接入诊断工具；不能以三个 binding
  复用 `ReadAttributes` 或新增说明文档，替代整组设施的必要性检查。
- **用户依据**：通用 6.1–6.2；用户关于遵循方案范围、合理风格统一及 PR 6992 冗余设施的补充。

### PRO-TUPLE-001：tuple 的类别语义与类型比较

- **适用条件**：DSL/parser、IR、codegen 等模块构造、传递或比较 tuple 类型。
- **检查内容**：按用户约定区分普通 tuple、数组、结构体、namedTuple 等类别，
  区分类别的额外信息存放在 `debugInfo` 中。判定类型一致时，不能仅调用 IR 的
  `struct_equal`（当前 Python 接口名为 `structural_equal`），还必须比较 tuple 类别信息；
  复用框架已有的语义类型比较能力，避免遗漏嵌套 tuple 的类别。
- **报告证据**：结构相同但类别不同的具体类型对、被忽略的 `debugInfo` 信息及错误比较位置。
- **源码入口**：[IR 类型](../../../../framework/include/ir/type.h)、
  [IRDebugInfo](../../../../framework/include/ir/debug_info.h)、
  [TupleTypeRegistry.types_equal](../../../../python/pypto_pro/language/parser/_tuple_type_registry.py)。
- **用户依据**：DSL/parser 3；IR 2；codegen 2。

### PRO-TARGET-001：目标架构、代码生成与执行一致性

- **适用条件**：修改架构选择、硬件相关代码生成、编译参数、跨核同步或 Cube/Vector 执行配合。
- **检查内容**：追踪当前输入经过架构解析、支持性校验、codegen、编译配置和 launch 的实际路径，
  核实这些环节的目标和约定是否一致。涉及指令语义时查阅对应依赖版本的源码或正式文档，
  不预设芯片型号、架构字符串或本机 pto-isa 路径。
- **报告证据**：实际支持的执行路径、具体不一致或指令约束、触发条件及结果。
- **反例**：存在架构枚举或配置项不等于对应 JIT 路径支持该架构；纯 Python 重构，
  或没有具体执行路径证据的推测性竞态，也不构成此类缺陷。
- **源码入口**：[架构解析](../../../../python/pypto_pro/runtime/platform.py)、
  [编译配置](../../../../python/pypto_pro/runtime/compile_config.py)、
  [JIT 校验与执行](../../../../python/pypto_pro/runtime/jit.py)。

### PRO-VALIDATE-001：验证证据与结论匹配

- **适用条件**：评价框架逻辑代码改动的验证证据，或执行检视所需的构建和测试；不用于检视测试代码自身。
- **检查内容**：按测试实际执行内容区分 parser/IR 行为、生成代码断言、编译验证及 NPU 运行验证；
  核实结果是否覆盖受影响行为。执行测试时确认源码、导入模块和原生构建产物对应待检视版本。
  根据目标版本的构建入口和测试配置选择必要用例，不固定硬件型号、构建命令或默认上板测试列表。
- **报告证据**：实际测试范围和结果，以及尚未覆盖的行为。
- **反例**：测试记录未提供不等于测试失败；Host 测试成功也不能证明跨核同步行为正确。
  缺少验证证据优先列为验证缺口，不能捏造功能缺陷。
- **源码入口**：[生成代码断言示例](../../../../python/tests/ut/pypto_pro/codegen/test_sync_all.py)、
  [运行测试入口](../../../../python/tests/st/pypto_pro/)。具体结论须结合实际断言、运行条件和结果。

## 扩展规则与回归案例

新增规则沿用“适用条件、检查内容、报告证据、反例、源码或文档依据”的结构，
并关联真实缺陷、可核实的接口契约或版本管理内的正式规范。
模块专属规则写入对应模块文件；通用或跨模块规则留在本文件，不复制到多个模块。
当前规则按用户提供的要求覆盖 DSL/parser、IR、Pass、codegen/backend、JIT/runtime；
后续依据实际 PR 检视结果调整，不因发现历史违规代码就自动放宽或删除规则。

补充规则可使用以下格式（示例为填写格式，不是生效规则）：

```markdown
### 规则编号：规则名称

- **适用条件**：哪些改动或输入会触发此规则。
- **检查内容**：必须满足或建议遵循的要求，明确区分两者。
- **报告证据**：判定违规时需要给出的具体证据。
- **反例**：允许的例外或看似违规但正确的情况。
- **源码或文档依据**：相关源码、正式规范或真实缺陷案例。
```

扩展时保存缺陷版本、修复版本和看似可疑但正确的案例；在独立会话中评测，避免把标准答案交给检视过程。
比较有无 skill 时的有效意见比例、已知缺陷命中、代码定位、耗时和误报。
当前基础版本未提供历史缺陷评测集；结构检查和评论通路验证不代表专业检视效果已验证。

用户反馈漏检时，先按评论对应版本逐项验证，区分成立、部分成立和证据不足；同一根因合并分析。
对照当次覆盖记录，区分规则缺失、规则不够具体与执行未落实，不能用新增规则掩盖已有规则未执行。
仅将已确认、可推广的判断补入对应规则，并保留阻止过度推广的反例。已知案例回放仅验证规则能否解释
该问题，不代表盲测召回率提升；用户仅要求复盘和优化 skill 时，不自动重发或回复 PR 评论。
