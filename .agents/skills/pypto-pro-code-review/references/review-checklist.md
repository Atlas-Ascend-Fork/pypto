# PyPTO Pro 模块索引与通用检视清单

## 使用方式

本文件维护模块索引和通用、跨模块规则；模块专属要求放在对应文件中，不重复定义。
按实际影响加载规则，不能只按目录选择。规则适用于框架逻辑，不检视 UT/ST 及测试辅助代码；
测试可作行为证据，排除的测试改动不计为覆盖缺口。源码链接只是阅读入口，既有实现不构成规则例外。

## 规则覆盖记录

每次检视随检查更新下表，并保留在报告中。全部通用规则及已加载模块的每条规则各占一行，
不能只列命中问题的规则；同时列明已加载模块及其余模块不适用的原因。

| 规则编号（链接原文） | 适用的改动文件 / 符号 | 检查状态 | 证据与结论 |
|---|---|---|---|
| 按实际规则填写 | 全部适用改动 | 已核对 / 不适用 / 未完成 | 代码位置、判断依据及关联发现编号 |

- **已核对**：全部适用位置和检查项已完成。列出违规对应的发现编号；没有违规也要说明依据，
  不能只写“通过”。已有同一条 PR 意见关联原评论，不能记作未发现违规。
- **不适用**：说明适用条件为何不成立，不能用测试通过或未发现功能问题代替。
- **未完成**：列出未覆盖位置、检查项或未决候选及原因，保留已完成部分的证据。

覆盖记录来自实际检查，不能先填结论。发现一处问题后仍须检查同规则的其他适用位置。
必要性证据须区分实际功能入口、最终消费者、明确外部交付需求，以及定义、导出、内部转发、
测试和文档引用；后几类引用不能单独证明功能必要。用途不明时记为未完成，不能先建议补齐配套。

## 模块索引

| 改动涉及 | 规则文件 | 加载条件 |
|---|---|---|
| DSL / parser | [dsl-parser.md](dsl-parser.md) | 用户语法、解析、作用域或从 DSL 构建 IR |
| Python IR / 原生 IR | [ir.md](ir.md) | IR 节点、类型、构造或语义约定 |
| Pass | [pass.md](pass.md) | 源码或 IR 的分析、优化、变换，以及 Pass 实现或接入 |
| CCE codegen / backend | [codegen-backend.md](codegen-backend.md) | IR 到生成代码的转换、op 注册或后端约束 |
| JIT / runtime | [runtime.md](runtime.md) | JIT、源码组装、编译配置、缓存或 kernel 执行 |
| 可选 pto-isa 深度契约检查 | [pto-isa-contract.md](pto-isa-contract.md) | 用户明确开启；不因涉及 op/codegen 自动加载 |

可选专项未开启时记为“未启用”，不计覆盖缺口；开启后其规则和逐约束记录纳入完成条件。
跨层 API 结合通用规则与接口所属模块检查。新增前端 op 加载 DSL 与 codegen 规则；
内部 IR call op 按实际构造、调用和后端路径加载，不要求补造前端层。
分析或变换功能即使位于其他目录，也须加载 Pass 规则。仅测试改动不触发模块规则加载。

## 模块职责

| 模块 | 职责与边界 |
|---|---|
| DSL / parser | 源码到 IR；仅保留构建 IR 必需的优化和 lowering，如 SSA、常量折叠、函数展开 |
| IR | 描述程序结构的通用数据结构；特定功能优先用现有 IR 和 call op 表达 |
| Pass | 代码结构的分析、优化、转换 |
| Codegen / backend | op 的后端声明与实现，以及 IR 到生成代码的转换 |
| JIT / runtime | 编译、运行时逻辑及框架流程串联，复用 JIT 与二进制模式的共同能力 |

## 通用及跨模块规则

### PRO-API-001：op 与公开 API 的跨层一致性

- **适用条件**：新增或修改前端 op，或公开 IR/codegen API 的签名、返回类型、语义变化。
- **检查内容**：先按暴露情况与真实调用链区分公开 API 和内部 call op，并按 `PRO-SIMPLE-001`
  核实新增接口的必要性；整组冗余时不能只建议补齐配套。公开 op 逐项对齐文档、API 原型、
  parser、IR 契约、backend 声明和实现的参数、返回值及语义；向 Python 暴露的原生 API
  同时核对 C++、binding、类型桩和封装。
  新增前端 op 先确认正式文档及目录入口存在、可达，再检查内容，不能因 diff 未含 docs 而跳过。
  docstring 仅在文档构建确实收录并提供入口时可作为正式文档。通用类型或控制流约束放在
  相应公共说明中，不误写成单个 API 的专属限制；内部表示变化不自动要求新增用户文档。
  无返回值要求见 `PRO-CODEGEN-001`；可选 ISA 专项未开启时不自动扩展为底层约束审计。
- **报告证据**：接口暴露依据、具体跨层差异及受影响的契约。文档缺失须列明查阅范围、目录入口
  和 docstring 收录情况，区分缺失与内容错误。
- **反例**：内部 call op 可以只在后端定义，按真实构造和消费链检查；不能仅凭缺少前端层认定
  违规或断言它仅供内部使用。公开接口不变的内部重构无需机械修改各层；未向 Python 暴露的
  原生接口无需补 binding。
- **源码入口**：[codegen binding](../../../../python/src/bindings/pypto_pro/codegen.cpp)、
  [类型桩](../../../../python/pypto/pypto_impl/codegen.pyi)、[Pro API 文档](../../../../docs/zh/api/pro_api/)。

### PRO-ERROR-001：输入校验与异常契约

- **适用条件**：新增 op，或调整 IR 构造、参数检查、错误处理。
- **检查内容**：逐参数识别约束和负责边界。前端输入优先在 parser/Python 校验；内部 op
  按实际构造边界检查，不为校验新增前端层。按以下顺序核对：
  1. 读取 `ir/_utils.py`，比较现有接口的输入表示与完整语义后复用。Python 整数判定不等于
     IR 整数类型判定，bool 是否属于合法整数也须明确；IR 类型校验遵循 `PRO-DSL-002`。
  2. 缺少能力时，从实际调用提炼有独立意义的校验原语，明确输入、成功结果、异常及边界。
     例如 Expr 类型、常量整数及可选左右界、常量整数容器及逐元素范围；边界可缺省时明确
     开闭语义。这些是契约示例，不要求预建全部接口，也不能把 op 整段业务校验搬进公共目录。
  3. 基础原语复用已有判断和取值能力，op 组合它们表达业务关系；区分“尝试获取”与
     “要求满足”的失败语义。支持常量和动态值的场景分别组合适用原语，不为复用而强制常量化。
     将原语与调用方一起检查，不能仅以每处都能报错证明职责合理。
  4. 对照参数绑定、解析后类型检查、原生推导和 codegen 的实际谓词与上游保证。
     已保证条件的重复校验按 `PRO-SIMPLE-001` 检查；谓词不同先识别缺口，不能直接删除。
     原生接口存在、被绑定或被 UT 调用不单独证明第二套校验必要，须找到独立入口契约或
     真实路径中尚未保证的条件。
  5. 区分输入错误与内部不变量，检查异常类型、错误码、源码位置及包装后行为是否符合
     项目定义、调用方捕获和原有契约，不按某组宏或异常名称机械判断。
- **报告证据**：触发输入、负责边界与具体契约偏差。重复检查给出两处谓词、到达路径和上游保证；
  复用或抽取问题给出现有能力、混合职责、原语契约及实际组合方，不能只建议“抽 helper”。
- **反例**：独立原生入口契约、只能在后端判断的硬件约束仍需适当校验；不要求所有 C++ 检查
  搬到 Python。一个职责可含多个相关条件，不将每个判断拆成函数，也不为一次性业务建立框架。
- **源码入口**：[异常定义](../../../../python/pypto_pro/_errors.py)、
  [公共校验](../../../../python/pypto_pro/ir/_utils.py)、
  [参数解析](../../../../python/pypto_pro/language/parser/_call_parser.py)。

### PRO-MODULE-001：模块独立性与职责边界

- **适用条件**：新增功能或调整其位置、交互方式，包括向既有函数添加分支。
- **检查内容**：沿输入、输出、策略决定处和消费者确定归属，不只看目录或类名。
  1. 按模块职责表分工；分析和变换按 Pass 规则接入，parser 只保留构建 IR 必需的处理。
     单个 op 的参数解释、后端约束和指令生成归该 op；公共 codegen 承担遍历、命名、类型
     转换、输出和通用上下文。backend 回调公共 codegen 中的 op 专用实现仍须检查职责错位。
  2. 新增回溯、旁表或重复计算来补足元数据时，追踪生产和传递链，定位最早失真或丢失处。
     若生产者按契约应保证该信息，优先从产生或变换处修复；“消费者需要该值”不是补偿设计
     必要的证据。核对静态/动态语义和受影响消费者，不能直接改读错误字段或只搬动补偿代码。
     上游历史问题也不能为新增补丁背书；修复需改变已确认方案时，先提出最小调整并取得确认。
  3. 模块内部同样区分编排与策略：编排层调用负责功能的入口，不拆解下层策略再零散传参。
     新增跨层适配前核实已有兼容接口是否足够，不能以当前方案所需参数反证该方案不可避免。
     kernel/caller 源码及编译配置的具体归属见 `PRO-RUNTIME-002`。
- **报告证据**：职责错位、策略泄露或信息丢失的生产者、传递点和消费者，及最小归属调整。
  合法独立分析须说明信息为何只能在该阶段获得；函数内部职责另按 `PRO-FUNCTION-001` 检查。
- **反例**：新增 API 必需的跨层联动不是散弹式修改；共享设施只有一个当前消费者也不自动违规。
  有独立阶段语义的分析不因重算某个值就必须移到生产者。

### PRO-FUNCTION-001：函数复用与参数必要性

- **适用条件**：新增或修改功能函数、入参、调用方式。
- **检查内容**：分别核对职责、复用和参数，不能以其中一项通过替代其他项。
  1. 按实际输入输出、状态读写和调用阶段拆分职责。查询若暗中承担独立的分析、求解或
     初始化，检查能否由负责阶段完成，使消费方只依赖稳定结果；移入私有 helper 不等于解耦。
     不能以函数名、const、长度或已有独立类代替判断。Pass 结果生命周期见 `PRO-PASS-002`。
  2. 与基线及现有函数比较，区分新增接口、既有入口扩展和调用位置变化。已抽取公共能力时，
     检查本次范围内所有同职责使用点；比较输入、前置条件、返回值、副作用与异常，确认仍有
     哪些路径自行实现了可完整复用的逻辑。找到一个消费者不等于完成复用，也不证明整组功能必要。
  3. 逐个核实参数的独立语义及来源，避免重复提取。共同控制一项功能的开关和配置须列出
     开启、关闭、默认及非默认组合，检查关闭时配置是否仍泄露到其他行为；配置只在开启时
     有意义时，评估一个可选配置是否足够。
     合并必须保留合法状态，不能把合法的零值随意当成关闭哨兵。
- **报告证据**：混合的职责及其阶段/依赖、可复用函数与绕过它的位置及语义对照，或参数组合
  的具体冗余。指出负责者与消费方式，不只要求“拆函数”或凭名字相似认定重复。
- **反例**：明确的按需计算、基于稳定结果的轻量派生查询可以保留，不要求 getter 都查表。
  职责或契约不同的实现不得强行合并；暂时停用但保留有实际用途的预设配置可有独立开关。

### PRO-DATA-001：数据结构的必要性与复用

- **适用条件**：新增数据结构，或表示迁移改变状态、字段的归属与维护方式。
- **检查内容**：说明结构表达的事实及生命周期，对比已有结构的字段、写入者和消费者。
  迁移后已由类型或运行时值承载的信息，不应继续由无独立用途的旁表、标志或来源分析维护。
  区分最终结果与仅用于推导的中间态，检查后者是否有必要持久保存或暴露给消费者。
  逐维检查状态粒度与已确认方案、消费需求是否一致。更细的索引、逐成员集合或关系信息，
  须说明相比更粗表示提供了什么必要能力；已有消费者不单独证明该粒度必要。比较简化前后
  的正确性、分析精度和生成代码代价，不能把精度降低等同于错误，也不能把更精确自动视为
  更合理。额外优化超出方案时，报告具体收益、代价和所需决策，不默认保留或删除。
  核实字段真实语义：分配基址不等于 view 起址，原容量不等于剩余容量，某来源的静态字段
  不能代表动态值。信息不准或缺失先按 `PRO-MODULE-001` 查生产者，不能直接据此新建结构。
  基础 IR 扩展按 [IR 规则](ir.md)，DSL 类型及 wrapper 按
  [PRO-DSL-005](dsl-parser.md#pro-dsl-005类型注解的表示与消费路径)核对。
- **报告证据**：新旧结构的字段、语义、有效范围及真实使用方对照，指出重复维护或不必要暴露。
- **反例**：分析过程所需的临时状态、具有明确失效条件的必要缓存，不因不是最终输出就自动冗余。

### PRO-SIMPLE-001：改动必要性与实现简洁性

- **适用条件**：所有本次新增或修改的逻辑。
- **检查内容**：按下列维度检查，不以“能运行”代替必要性和一致性。
  1. **范围**：对照目标与已确认方案，逐个核对可独立撤销的修改，细至复合条件和相邻分支。
     区分精确类型匹配与包含子类的匹配；当前类型集合下结果相同不代表扩展语义相同。
     风格统一限于本次相关、明确需要一致且语义相同的写法，不为对称而扩大适配范围。
  2. **整组用途**：将新增 API、hook、标记及 helper 作为整体，追踪功能入口如何启用、
     结果由谁消费。可选回调核对实际非空传入；binding 继续追踪导出后的用途。
     组内互相调用、自带测试/文档/版本探针不能单独证明交付需要；无真实消费者和明确外部需求
     时报告冗余，不能假设未来工具会使用。
  3. **完整复用**：公共入口或类型别名确有用途后，继续检查同语义角色的声明、构造及使用点
     是否一致采用。无独立契约却绕过已有入口、重新实现或混用表示，即使结果不变也须报告。
     函数复用的语义对照按 `PRO-FUNCTION-001` 执行，不扩为全仓替换。
  4. **冗余防御**：将新增拒绝、默认值、截断、跳过、变换后复查及旧表示兼容分支与上游保证逐项
     对照。仅重复拒绝同一非法输入，或验证自身变换已完成而不承担独立约束的逻辑，须核实
     是否必要。追踪全部实际入口的归一化后置条件；旧实现或手工构造测试能命中不证明生产
     路径需要兼容。识别独立约束后分别处理，不能连同重复部分一起删除。
     对复合过滤条件逐项核对输入域，区分空指针、合法占位值和不参与分析的类型；不能把它们
     都视为非法输入而删除处理，也不能用其中一项必要为整个条件背书。
- **报告证据**：范围问题给出独立子改动、原语义及适配必要性；用途问题给出检索范围、引用
  分类及整组功能的交付关系；复用问题给出统一约定、绕过位置及等价依据；防御问题给出谓词、
  到达路径与上游保证。不能只写“代码不够简洁”。
  检索生成代码中的别名、成员和变量时，沿字符串拼接检查产物消费者；定义与使用由不同
  生成函数发射不等于无用。无字面引用也不能排除动态注册或明确外部调用。
- **反例**：已授权重构、必要迁移、有明确一致性需求且语义不变的风格调整不因能局部回退就
  算多改。独立 verifier、跨 Pass 不变量、外部输入检查和有明确用途的调试断言不因执行较晚
  就算过度防御。明确交付外部的 API 无需仓内调用；本次自行新增的配套说明不单独构成交付依据。

### PRO-TUPLE-001：tuple 的类别语义与类型比较

- **适用条件**：构造、传递或比较 tuple 类型。
- **检查内容**：普通 tuple、数组、结构体、namedTuple 等类别的额外信息存于 `debugInfo`。
  判定类型一致须同时比较结构和类别，不能只用 IR `struct_equal`（Python 为 `structural_equal`）；
  复用框架语义比较能力，并覆盖嵌套 tuple。
- **报告证据**：结构相同、类别不同的具体类型对，被忽略的信息及比较位置。
- **源码入口**：[IR 类型](../../../../framework/include/ir/type.h)、
  [IRDebugInfo](../../../../framework/include/ir/debug_info.h)、
  [语义比较](../../../../python/pypto_pro/language/parser/_tuple_type_registry.py)。

### PRO-TARGET-001：目标架构、代码生成与执行一致性

- **适用条件**：修改架构选择、硬件代码生成、编译参数、跨核同步或 Cube/Vector 配合。
- **检查内容**：追踪实际输入的架构解析、支持性校验、codegen、编译和 launch 路径，对齐目标

## 规则维护

规则用于指导下一次独立检视，不承担个案复盘存档。更新时遵循以下步骤：

1. **确认缺口**：按反馈对应版本核实问题及反例，对照覆盖记录区分标准缺失、表达不够可执行、
   已有规则未落实。执行遗漏先修流程或证据要求，不重复新增同义规则。
2. **提炼判断**：写出可迁移的约束及适用条件、检查步骤、判定证据和边界。用不同名称和模块
   的同类实现检查规则是否仍成立，不能依赖某个 PR、评论编号、符号名或当时的错误结论。
3. **归并职责**：同根因优先补强现有规则；通用要求集中在本文件，模块规则只补充专属契约，
   SKILL.md 只维护执行流程。必要示例只解释难以区分的语义边界，不累计历史叙述或原始对话。
4. **检查过度推广**：保留合法反例；清理前后核对原要求与边界，不能借精简弱化约束，也不能
   从单例推出新限制、扩大改动范围或要求不必要的抽象。
5. **验证变化**：核对规则覆盖、重复定义、链接及结构；用有缺陷和看似可疑但正确的代表场景
   检查可操作性。已知答案回放只验证规则能解释案例，不能宣称盲测召回率提升；有独立评测时
   另记命中、定位、误报和成本。优化 skill 不自动授权修复源码或重发、回复 PR 评论。
