# PyPTO Pro Code Review

默认同时检视功能正确性和实现规范。用户要求“仅检查规范”时，只输出适用规则确认的规范违规，
不开展额外功能缺陷排查；仍须沿源码确认规则适用条件、实际契约和反例，不以运行失败为报告前提。
规则文件是必须执行的检查标准；测试通过或发现若干功能问题，
不能替代逐条规则检查。只报告有代码证据的问题，不因影响轻微而省略已确认的规范违规。

## 范围与入口

- 接收 PR 链接或编号、提交范围、文件路径或本地未提交改动。
- 核心范围为 `python/pypto_pro/`、`framework/include/pypto_pro/`、
  `framework/src/interface/pypto_pro/`；沿实际调用链纳入共享 IR、Pass、binding 和类型桩。
- UT/ST、golden 及相关测试辅助逻辑按[测试规则](references/test.md)检视；
  若范围内只有测试改动，同样适用。测试也可读取和执行以验证框架行为。
- 检视不自动授权修复源码或发布评论。GitCode PR 默认只返回报告；只有用户明确要求或确认
  向目标 PR 发布时才写入，已有授权不重复确认。链接或单独调用技能不构成发布授权。
- 检视依据为用户要求、适用项目指令、目标版本源码及正式契约。既有违规实现不能作为例外；
  只报告本次引入或扩大的问题。不将机器配置中的硬件、路径、构建命令或测试列表固化为通用规则。

## 可选：pto-isa 深度契约检查

默认关闭。仅在用户明确开启，或明确要求结合 pto-isa 实现检查前端非法参数拦截时，读取并执行
[专项规则](references/pto-isa-contract.md)。普通“全面检视”或 API 一致性检查不自动开启。
默认从远端取得检查开始时最新的 pto-isa `master` 并固定 SHA；用户指定其他基线时从其约定。
范围为本次影响的接口，不扩为全仓审计。

基础检视为具体疑点查看一处依赖实现不等于开启专项。未开启时注明“未启用”，不记为覆盖缺口；
开启后将其规则和逐约束记录纳入完成条件，缺少基线时不得静默降级或宣称专项完成。

## 执行流程

### 1. 主 agent 固定对象并准备材料

默认由主 agent 编排一轮检视。已经收到 `functional`、`rules` 或 `verifier` 角色的子 agent
只执行本角色步骤，不再次委派整轮流程。自动修复与轮次控制由
[审核修复工作流](../pypto-pro-review-fix/SKILL.md)负责，单独调用本技能仍只授权检视。

- **PR**：按 [GitCode 工作流](references/gitcode-workflow.md) 只读获取状态、实际目标分支、
  base/head SHA、完整 diff 和对应源码。比较基点来自 PR 信息，不假定 `upstream/master`；
  不切换或覆盖用户工作区。明确要求检视草稿 PR 时照常进行。
- **Commit 评论**：按链接中的 SHA 获取该提交及评论，不能因 URL 带 `prId` 就改用 PR 评论。
- **本地改动**：遵循用户指定范围；未指定时检查 `git diff --cached`、`git diff` 及相关未跟踪源码，
  区分索引和工作区版本，不遗漏新增源码，也不读取无关日志或二进制产物。
- 将范围内的测试及 golden 改动纳入清单。缺少决定检视对象的信息时才询问；
  缺少部分源码时继续可独立完成的检查。
- 首次独立检视先保存发现及复核结果，再由主 agent 读取已有评论进行去重；定向复核按用户指定意见执行。

将客观材料一次性保存在任务专属临时目录，向各角色传递路径及简短任务说明：

- 用户需求、已确认方案及来源、范围和兼容性边界；未提供的内容明确标注，不替用户编造方案。
- 仓库路径、项目指令与本技能路径、检视模式、固定版本、原始 diff 及变更文件清单。
- 已有验证的命令、结果、对应版本和日志路径；原始记录可读取，不以作者自评代替。
- 复审时提供上轮受审版本、问题台账及报告；用户指定已知问题时保留原要求并注明定向复核。

主 agent 统一获取 PR 材料并安排验证。各角色复用同版本的原始验证记录，
仅在代码变化或具体疑点使证据不足时追加验证。
准备阶段只共享原始源码、版本、diff 和客观索引，不把主 agent 推导的调用关系或结论当作事实输入。
按调用链批量读取完整函数及必要依赖；已读内容有版本依据时复用，出现缺口才追加读取。

不传递开发过程中的推测、自评、废弃方案或无关对话。主 agent 不预先过滤候选范围；
两个 reviewer 首次发现前不共享结论，也不读取已有 review 答案。
PR 使用固定 SHA 读取源码；本地保存索引/工作区 diff、相关未跟踪源码及所读文件的版本证据，
不切换、stash 或覆盖用户工作区。受审内容变化时重新核对受影响结论，不混用版本。

- **完整检视**：读取原始任务基点到当前版本的全部 diff，放回完整函数、类型、模块及调用链中检查。
- **增量检视**：读取上轮受审版本以来的 diff，复核全部未解决问题及受影响的上下游；
  沿用有版本依据且未受影响的覆盖记录，明确区分沿用与本轮核对。核对源码、规则、实际目标分支、
  依赖及契约；文件未改不能单独证明覆盖有效。保留原记录和独立复核依据，失效项重新检查。
  无可靠上轮版本或报告时执行完整检视，原始任务基点不因修复或方案调整改变。
  修改 skill 的通用执行流程会影响所有规则，其能力验证使用完整范围，不能仅测改动的规则文字。

### 产物保存与角色收束（各角色共用）

- 开始角色任务时创建产物文件，记录固定版本、职责和待查范围。每完成一个候选、行为路径或
  一条调用链就保存证据与结论，通知主 agent 哪些记录可交复核；不等整篇报告整理完成才首次写入。
  按[记录协议](references/review-records.md)维护一份证据和覆盖记录，问题说明与双向视图引用同一证据。
  批次是同一角色的分批交接，不新增审核轮次或为每批重建 agent。后续修订已交接记录时保留原版本，
  显式列出失效的证据、覆盖及候选 ID，交 verifier 重新核对受影响部分。
- 主 agent 以新增的源码证据、已完成覆盖项、验证结果或已保存记录判断进度；角色仍在运行、
  反复报告“正在整理”或文件仅有标题，均不能证明实质进展。只有产物可读、所需覆盖和缺口已记录，
  角色才能报告完成并进入后续阶段。
- 连续进度检查没有实质变化时，先要求角色保存已完成部分，并列明剩余项及具体阻塞。
  若只剩整理，要求下一步直接小批写入；需要中断恢复时保留原角色上下文、版本和已有产物，
  从剩余项继续，不以反复催促、重复中断或重启整轮检视代替处理阻塞。
- 所需范围检查及记录完成后，角色立即交接；仅为未决候选、覆盖缺口或版本变化补查。
  已有充分证据的条目不为润色重做搜索或验证。主 agent 直接复用已复核条目汇总，
  不让报告整理成为新一轮检视。收束不得省略适用规则、确认问题或必要验证；确实无法完成时明确交付缺口。

### 2. 两个独立 reviewer 并行检视

每轮新建不继承开发对话的 reviewer，显式使用 `fork_turns="none"`，模型与推理设置沿用当前配置。
仅规范模式只创建规则 reviewer。独立 agent 不可用时报告流程未完成，不静默回退为开发上下文自检。

| 角色 | 职责与输出 |
|---|---|
| `functional` | 核对需求、回归、边界输入、类型/状态传播、生成代码与运行时契约；给出触发路径、实际后果、候选及已检查行为路径和缺口 |
| `rules` | 执行全部适用通用及模块规则；给出规则编号、适用条件、证据、反例及完整规则覆盖表 |

两个角色均读取适用项目指令和客观材料，按完整函数、类型及必要调用链读取源码。
功能 reviewer 按需读取相关契约的完整规则条目和反例，
不重复制作规范覆盖表；规则 reviewer 沿真实调用链理解语义，不额外重做一次全面功能搜索。
交叉问题均可记录，不能因归属另一角色而丢弃。测试仍按测试专属规则判断。

涉及新增执行模式或共享实例化入口时，两个角色均读取 `PRO-DSL-007` 及其引用的公共规则，
先列实际调用域、模式和角色，再判断新增分支的覆盖。逐函数检查和现有模式的测试通过，
不能替代这个模式对照；设计调整与既有契约下的缺陷分别报告。

以下逐条覆盖由规则 reviewer 负责；功能 reviewer 同样核对实际调用链、版本和行为证据：

先完整读取 [模块索引与通用规则](references/review-checklist.md)，再按实际影响加载对应模块规则。
跨层影响不能只按目录判断；新增内部 call op 也须加载 codegen 规则核对注册和构造，
不自动要求 DSL 配套；新增分析/变换则须加载 Pass 规则。测试及 golden 改动加载测试规则。
不要只搜索规则编号或摘要。

1. 列全修改的函数、状态、类型、注册点及全部适用规则；模块加载与不适用条件同样记录。
   主 agent 固定文件/规则清单，reviewer 补全修改点，不能通过删减清单制造完成。
2. 以声明、生产者、传递过程、消费者组成的调用链为阅读单位，一次读取后应用所有相关规则。
   同一源码事实只保存一次，各条规则分别判断并引用它；不按每条规则从头重读相同调用链。
   必要性、职责、复用与行为正确性是不同判断，不能用同一句“有消费者”替代。
3. 核对每个局部分支及状态的输入来源、表达事实和消费需要。新增校验、Pass 调用和跨对象查询
   分别确认负责入口与上游保证；模块归属正确、使用公共工厂、已有消费者均不能单独证明必要。
   比较 base 行为；涉及公共构造或操作数消费时，再核对固定目标分支的接口迁移和表示。
4. 持续维护一份记录，由它生成规则到修改点、修改点到规则的视图，并逐项核对遗漏。
   双向覆盖不能抽样，脚本只校验记录完整性，不替代源码判断。无问题项简记依据；候选和争议项
   详记契约、触发路径、反例及结论，不重复撰写多份证据说明。新模块影响须补读规则并更新清单。

具体判断标准集中在规则文件；执行时逐项检查，不能用模块概括或问题数量替代覆盖证据。

### 3. 独立 verifier 分批逐项复核

第一批可复核记录保存后，即新建 `fork_turns="none"` 的 verifier，输入同一任务、固定版本和产物路径，
与尚在检视的 reviewer 并行工作。没有并行容量时等待可用角色结束，不省略独立复核。
它不继承 reviewer 对话，把候选作为待验证假设；对已完成的覆盖批次也逐项回到原始源码核实。
reviewer 首次发现全部保存前，verifier 反馈仅交主 agent 保管，不回传影响尚未完成的发现；
取证所需的客观文件可以补充。首次发现结束后再交回反例、分歧及新增候选处理。
每项输出稳定编号及“确认 / 否定 / 证据不足”，
附源码、契约或反例依据；同根因合并，保留全部相关位置和两类证据，不能按 agent 数量重复计数。
复核中新增的候选交给对应 reviewer 核实，不由提出者单独自证；无法解决的分歧保留为未决项。

逐项检查功能路径和规则覆盖记录的范围、适用性、证据与结论。按文件、符号和行位置回到源码及
规则原文，证据不足时扩大追踪范围，不从头重复两个 reviewer 的完整问题搜索。
零候选时也检查覆盖；仅有编号、链接或“通过”不能证明检查完成，不通过抽样缩减适用检查。
后续批次复用同一个 verifier；已复核且未变化的记录不重新完整检查。全部 reviewer 完成后，
核对最终记录版本、所有批次、全部候选与覆盖缺口再收束，早期批次通过不代表整轮完成。

- **功能缺陷**：给出目标版本的位置、可触发输入/控制流、实际后果与修复方向；
  shape、dtype、layout、时序或性能问题须有具体路径及相应证据，不能只有“可能”。
- **规范违规**：给出规则编号、适用条件及违反要求的实现，不要求虚构运行时错误。
  明确的规范约束不能降格为个人风格偏好，也不能因严重性低或已有类似代码而忽略。
- 主动查找反例：上游保护、归一化、合法转换、独立入口契约及目标条件是否排除了问题。
  区分功能错误、实现规范问题和验证缺口；不把缺少测试、环境失败直接当成功能缺陷。
- 验证使用目标版本的构建入口和测试配置，确认源码与导入产物一致；分别记录源码推导、Host、
  编译和设备运行证据。检视本身不授权修改被检代码。

各角色将完整候选、覆盖及复核记录写入任务产物，仅回传状态、计数、缺口和文件路径。
问题保留稳定编号，复审区分本轮引入、此前漏检和修复后复发；作者声称已修复不能替代复核。
原始报告及否定依据保留，不能在读评论或修复后覆盖首次独立检出的记录。

### 4. 检查完成条件

- 本轮所需 reviewer 和 verifier 均完成，且源码版本一致；部分角色失败不能由其他角色的结果代替。
- 每条通用及已加载模块规则都有覆盖记录；所有适用改动已核对，不适用项有理由。
- 新增设施已追踪到实际功能入口和消费者，或有明确外部交付契约；函数职责与状态生命周期已核对。
- 类型/表示迁移、上游保证及下游补偿已沿完整链检查，不能以现有错误或缺失为不可改变的前提。
  修复超出用户方案时报告所需最小调整，不自动扩展实现范围。
- 所有确认的问题已进入清单或关联已有意见；测试改动已按测试专属规则完成检视。
- 缺失源码、规则、未决候选和未覆盖路径均已列明；存在缺口时只能报告部分完成。
  缺少验证证据与没有发现问题分别陈述，不能互相替代。

### 5. 输出或发布意见

先形成完整报告。发布授权及范围按“范围与入口”判断；尚未授权的 PR 检视，先返回报告，
再询问是否发布，并链接本技能、引用“只有用户明确要求或确认向目标 PR 发布时才写入”说明原因。
本地检视、用户要求仅返回报告或没有待发布意见时不请求发布确认。

取得授权后按 [GitCode 工作流](references/gitcode-workflow.md) 提交，复查 head、去重并回读位置。
返回逐条评论 ID、位置、回读状态及 PR 链接；成功部分不重复提交，失败与未验证分别说明。

## 输出约定

先列全部确认问题，按严重程度排序，再附规则覆盖表及验证情况。每条意见包含：

- 文件、行号、Blocker / Major / Minor、功能缺陷或规范违规、简短标题；
- 触发或适用条件、代码证据、影响及修复方向；规范违规链接对应规则。

级别按实际影响判断，编译/执行受阻或错误结果等重大问题优先；轻微且明确的规范问题可列为 Minor。
报告注明范围、目标 SHA（适用时）、所加载规则、测试检视范围及验证缺口。
完整覆盖且无确认问题时，说明“在本次范围内未发现有充分证据的问题”；
部分完成时只陈述已检查范围的结论和剩余工作，不以“没有问题”概括未检查部分。

完整报告只形成一次，复用已核实条目；可交付完整产物链接和简短摘要，完整问题及覆盖记录仍须可读。
无候选与无覆盖缺口分别陈述。主 agent 不能以开发自评删除确认问题，有新证据时退回复核。

## 维护规则

用户反馈漏检时，按[规则维护要求](references/review-checklist.md#规则维护)改进可执行的判断标准。
优化执行方式时，以当前有效 skill 为基线，固定源码、规则版本、模型配置及原始输入做独立对照。
回归包括已确认问题、已修复版本及合法反例；预期答案由主 agent 保管，不提供给首次 reviewer。
同时检查检出、误报、全部适用覆盖和证据质量，再比较角色耗时、整轮耗时及重复读取/输出成本。
通用流程改动使用完整范围并重复验证；漏掉已知问题或降低覆盖时继续修订，不以变快作为通过依据。
