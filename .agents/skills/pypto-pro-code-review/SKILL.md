# PyPTO Pro Code Review

默认同时检视功能正确性和实现规范。用户要求“仅检查规范”时，只输出适用规则确认的规范违规，
不开展额外功能缺陷排查；仍须沿源码确认规则适用条件、实际契约和反例，不以运行失败为报告前提。
规则文件是必须执行的检查标准；测试通过或发现若干功能问题，
不能替代逐条规则检查。只报告有代码证据的问题，不因影响轻微而省略已确认的规范违规。

## 范围与入口

- 接收 PR 链接或编号、提交范围、文件路径或本地未提交改动。
- 核心范围为 `python/pypto_pro/`、`framework/include/pypto_pro/`、
  `framework/src/interface/pypto_pro/`；沿实际调用链纳入共享 IR、Pass、binding 和类型桩。
- UT/ST、golden 及相关测试辅助逻辑按[测试规则](references/test.md)检视；
  若范围内只有测试改动，同样适用。测试也可读取和执行以验证框架行为。
- 检视不自动授权修复源码或发布评论。GitCode PR 默认只返回报告；只有用户明确要求或确认
  向目标 PR 发布时才写入，已有授权不重复确认。链接或单独调用技能不构成发布授权。
- 检视依据为用户要求、适用项目指令、目标版本源码及正式契约。既有违规实现不能作为例外；
  只报告本次引入或扩大的问题。不将机器配置中的硬件、路径、构建命令或测试列表固化为通用规则。

## 可选：pto-isa 深度契约检查

默认关闭。仅在用户明确开启，或明确要求结合 pto-isa 实现检查前端非法参数拦截时，读取并执行
[专项规则](references/pto-isa-contract.md)。普通“全面检视”或 API 一致性检查不自动开启。
默认从远端取得检查开始时最新的 pto-isa `master` 并固定 SHA；用户指定其他基线时从其约定。
范围为本次影响的接口，不扩为全仓审计。

基础检视为具体疑点查看一处依赖实现不等于开启专项。未开启时注明“未启用”，不记为覆盖缺口；
开启后将其规则和逐约束记录纳入完成条件，缺少基线时不得静默降级或宣称专项完成。

## 执行流程

### 1. 固定检视对象

- **PR**：按 [GitCode 工作流](references/gitcode-workflow.md) 只读获取状态、实际目标分支、
  base/head SHA、完整 diff 和对应源码。比较基点来自 PR 信息，不假定 `upstream/master`；
  不切换或覆盖用户工作区。明确要求检视草稿 PR 时照常进行。
- **Commit 评论**：按链接中的 SHA 获取该提交及评论，不能因 URL 带 `prId` 就改用 PR 评论。
- **本地改动**：遵循用户指定范围；未指定时检查 `git diff --cached`、`git diff` 及相关未跟踪源码，
  区分索引和工作区版本，不遗漏新增源码，也不读取无关日志或二进制产物。
- 将范围内的测试及 golden 改动纳入清单。缺少决定检视对象的信息时才询问；
  缺少部分源码时继续可独立完成的检查。
- 评估能否检出已有意见时，先固定源码并保存独立发现，再读取评论。按位置和版本区分独立检出、
  部分命中和读评论后补查；相同规则命中另一位置不算命中原意见。已知答案的回放不是盲测。

### 2. 逐条执行规则检视

先完整读取 [模块索引与通用规则](references/review-checklist.md)，再按实际影响加载对应模块规则。
跨层影响不能只按目录判断；新增内部 call op 也须加载 codegen 规则核对注册和构造，
不自动要求 DSL 配套；新增分析/变换则须加载 Pass 规则。测试及 golden 改动加载测试规则。
不要只搜索规则编号或摘要。

1. 建立规则覆盖表：所有通用规则及已加载模块的每条规则各占一行，记录适用符号和调用链；
   不适用要说明条件为何不成立。
2. 双向核对覆盖：从每条规则检查全部适用改动，再从每个修改的函数、状态、类型及注册点反查
   是否遗漏规则。不能抽样，也不能只检查模块归属而略过函数内部职责。
   对新增状态维度和语义分支，分别记录实际输入来源、表达的事实及消费需要；整个函数有用途
   或结果正确，不能替代这些局部必要性证据。
3. 沿声明、生产者、传递过程、消费者核对真实契约；检查 base 行为，区分新增问题与历史问题。
   对接口、函数和数据结构分别确认必要性、职责、完整复用及行为正确性；一个维度成立不替代其他维度。
   PR 涉及公共构造或操作数消费时，同时检查已固定目标分支的框架接口与类型表示；
   目标分支已发生迁移而 head 尚未包含时，单列集成规范问题及两个版本的证据。
4. 覆盖记录写明代码证据和反例。接口存在、已导出、使用了 visitor、声明为 const、测试通过，
   均不能单独证明必要性、解耦或正确性。遇到新模块影响，补读规则并更新覆盖范围。

具体判断标准集中在规则文件；执行时逐项检查，不能用模块概括或问题数量替代覆盖证据。

### 3. 复核候选问题

- **功能缺陷**：给出目标版本的位置、可触发输入/控制流、实际后果与修复方向；
  shape、dtype、layout、时序或性能问题须有具体路径及相应证据，不能只有“可能”。
- **规范违规**：给出规则编号、适用条件及违反要求的实现，不要求虚构运行时错误。
  明确的规范约束不能降格为个人风格偏好，也不能因严重性低或已有类似代码而忽略。
- 主动查找反例：上游保护、归一化、合法转换、独立入口契约及目标条件是否排除了问题。
  区分功能错误、实现规范问题和验证缺口；不把缺少测试、环境失败直接当成功能缺陷。
- 同一根因合并意见，保留所有相关位置和规则；不重复已有的同一条意见。允许零条发现。
- 验证使用目标版本的构建入口和测试配置，确认源码与导入产物一致；分别记录源码推导、Host、
  编译和设备运行证据。检视本身不授权修改被检代码。

### 4. 检查完成条件

- 每条通用及已加载模块规则都有覆盖记录；所有适用改动已核对，不适用项有理由。
- 新增设施已追踪到实际功能入口和消费者，或有明确外部交付契约；函数职责与状态生命周期已核对。
- 类型/表示迁移、上游保证及下游补偿已沿完整链检查，不能以现有错误或缺失为不可改变的前提。
  修复超出用户方案时报告所需最小调整，不自动扩展实现范围。
- 所有确认的问题已进入清单或关联已有意见；测试改动已按测试专属规则完成检视。
- 缺失源码、规则、未决候选和未覆盖路径均已列明；存在缺口时只能报告部分完成。
  缺少验证证据与没有发现问题分别陈述，不能互相替代。

### 5. 输出或发布意见

先形成完整报告。发布授权及范围按“范围与入口”判断；尚未授权的 PR 检视，先返回报告，
再询问是否发布，并链接本技能、引用“只有用户明确要求或确认向目标 PR 发布时才写入”说明原因。
本地检视、用户要求仅返回报告或没有待发布意见时不请求发布确认。

取得授权后按 [GitCode 工作流](references/gitcode-workflow.md) 提交，复查 head、去重并回读位置。
返回逐条评论 ID、位置、回读状态及 PR 链接；成功部分不重复提交，失败与未验证分别说明。

## 输出约定

先列全部确认问题，按严重程度排序，再附规则覆盖表及验证情况。每条意见包含：

- 文件、行号、Blocker / Major / Minor、功能缺陷或规范违规、简短标题；
- 触发或适用条件、代码证据、影响及修复方向；规范违规链接对应规则。

级别按实际影响判断，编译/执行受阻或错误结果等重大问题优先；轻微且明确的规范问题可列为 Minor。
报告注明范围、目标 SHA（适用时）、所加载规则、测试检视范围及验证缺口。
完整覆盖且无确认问题时，说明“在本次范围内未发现有充分证据的问题”；
部分完成时只陈述已检查范围的结论和剩余工作，不以“没有问题”概括未检查部分。

## 维护规则

用户反馈漏检时，按[规则维护要求](references/review-checklist.md#规则维护)改进可执行的判断标准。
不把具体 PR 的解释、对话或漏检经过追加成规则；规则增强与已知案例回放、独立盲测的效果分别记录。
