# PyPTO Pro Code Review

围绕本次改动同时检视功能正确性和规则符合性，输出可定位、可验证、可修复的检视意见。
`references/` 中的通用及模块规则是必须执行的检视标准，不能只作背景阅读。
对纳入范围的框架逻辑代码，必须逐条核对适用规则并提供覆盖记录；发现功能缺陷或测试通过均不能替代规则检视。

## 范围与入口

- 接收 PR 链接或编号、指定提交范围、文件路径或本地未提交改动。
- 核心范围：`python/pypto_pro/`、`framework/include/pypto_pro/`、
  `framework/src/interface/pypto_pro/` 及对应 binding 中的框架逻辑代码。
- 共享 IR、Pass（`framework/include/ir/transforms/`、`framework/src/interface/ir/transforms/`）、
  类型桩等改动根据实际调用链纳入，不仅按目录名判断归属。
- UT/ST 及仅供测试使用的辅助代码不在检视范围内，不对测试自身产生功能或规范检视意见。
  可读取或执行测试以验证框架行为；测试专属检视规则待用户另行补充，不沿用本技能规则。
- 用户指定 GitCode PR 进行检视时，默认只返回报告，不向 PR 写入意见。仅在用户明确要求或确认
  将检视意见更新到该 PR 后发布；单独提供 PR 链接或调用本技能不构成发布授权。
  用户已明确要求发布时直接执行，无需重复确认；本地检视只返回报告。
- 本地检视需要 Git 和源码；GitCode 发布另外依赖 Python 3、网络、有效凭据及仓内现有提交脚本。

显式调用示例：

```text
$pypto-pro-code-review 检视 <PR链接>
$pypto-pro-code-review 检视 <PR链接>，并将检视意见更新到 PR
$pypto-pro-code-review 检视本地未提交的 pypto-pro 改动
```

## 执行流程

### 1. 固定检视对象

检视依据来自用户明确要求，以及目标版本的源码、测试和正式文档。
用户提供的检视要求已整理在本技能的规则文件中，应作为明确的检视标准。
仓内已有实现即使违反这些规则，也不能作为放宽规则或认可新增同类实现的依据；
源码用于定位和取证，本次 PR 未引入或扩大的历史问题不纳入意见。
本技能不读取 `CLAUDE.md` 或 `.claude/` 文件作为检视依据，不将本机配置中的硬件目标、
环境路径、构建命令或测试列表固化为规则。

- PR：读取目标仓库、状态、base/head SHA 和 diff，记录本次检视的 head SHA。
  按 [GitCode 获取与提交说明](references/gitcode-workflow.md) 的只读获取步骤取得完整改动及对应源码。
  从实际 PR 信息确定目标分支与比较基点，不假定存在 `upstream/master`，不切换或覆盖用户当前工作区。
- Commit 评论：按链接中的 commit SHA 获取评论；即使链接带 `prId`，也不能用 PR 评论替代。
  只读获取及位置缺失时的处理见同一份 GitCode 说明。
- 本地改动：遵循用户给定范围；未指定时检查 staged 和 unstaged diff，列出相关未跟踪源码，
  使用 `git diff --cached`、`git diff` 和 `git ls-files --others --exclude-standard` 确认范围。
  区分索引与工作区版本，避免遗漏新增文件或读取无关日志、二进制产物。
- 根据路径和实际用途排除 UT/ST（包括 Python、C++ 测试及测试辅助代码），在范围说明中列明，
  不将其计为规则覆盖缺口。若改动仅包含 UT/ST，直接说明本技能不适用，不生成检视意见。
- 明确请求检视草稿 PR 时照常检视。缺少决定检视对象的信息时才询问用户。

### 2. 逐条执行规则检视并分析功能

先读取 [模块索引与通用检视清单](references/review-checklist.md)，再按其中的模块索引
完整读取相关规则文件，不能只搜索规则编号或阅读摘要。通用及跨模块规则只在清单中维护，
不在模块文件中重复。
规则选择同时考虑改动目录和实际影响关系；一个 PR 涉及多个模块时加载对应的多个文件，
不默认读取全部模块规则。新增暴露给前端的 op 同时加载 DSL/parser 和 codegen/backend 规则；
仅供框架内部使用的 IR call op 加载 codegen/backend 及实际构造、调用路径涉及的模块规则，
不因新增内部 op 就要求补齐前端层。
新增源码或 IR 分析、优化、变换功能时加载 Pass 规则，即使改动不在 Pass 目录。

按清单中的“规则覆盖记录”要求执行，不能在找到若干功能问题后跳过或终止规则检视：

1. 从实际读取的文件列出全部通用规则及所加载模块的全部规则，逐条判断适用条件，
   将适用规则映射到本次改动的文件、符号及受影响调用链；不适用须给出原因。
2. 对每条适用规则核对其全部适用改动及检查内容，记录代码证据、候选违规和反例。
   同一规则命中一处后仍须检查其他适用位置，不能抽样后宣称全量覆盖。
   同一位置也须拆开检查项：API 文档是否存在与内容是否一致、参数是否被使用与是否必要、
   模块归属与模块内函数职责，分别给出依据。某一项成立不能代替其他项。
3. 从 diff 中的符号向声明、调用方、注册、binding 和测试追踪，分析功能正确性，
   并反向检查每个改动文件及主要符号是否遗漏适用规则。发现新的模块影响时补读规则并更新记录。
4. 按 `PRO-SIMPLE-001` 核对改动必要性与语义边界。复合条件和相邻分支分别核对，
   不能用其中一处必要修改为整段改写背书；风格统一须有明确的一致性需求且保持各处原有语义。
   对新增接口、回调及其辅助设施，从实际功能入口追踪到最终消费者，或核实明确的外部交付契约；
   不能停在导出、绑定或 helper 之间的调用。先判断整组新增代码是否需要，再提出补齐各层接口的建议。

职责边界的覆盖证据须落到新增或迁移的实现函数、状态及调用方，不能仅以“属于后端”或
“使用 IR type”等模块概括判定符合。安全性判断须追踪到实际保护条件；有上游保护的可疑访问
不能报告为可触发故障，局部表达不清与功能错误应分别判断。
校验逻辑还须按 `PRO-SIMPLE-001` 核对其必要性，不能因它能够拦截错误就认定没有冗余。

PR 检视所读源码和测试应对应记录的 head SHA，避免将本地其他版本的实现当作 PR 上下文。
发现候选问题后检查 base 中的行为，区分本次引入或扩大的问题与已有问题。

### 3. 复核候选问题

按问题类型复核证据：功能缺陷需说明代码位置、触发条件、实际后果；规范违规需指出规则编号、
适用条件及具体违反要求的代码。明确的规范违规可以独立成立，不要求虚构运行时故障来证明。
不得因测试通过、暂未发现运行时后果、级别较低或仓内已有同类写法而过滤明确的规则违规；
规则明确约束的实现方式不能降格为个人风格偏好。
用调用链、接口约定或必要的针对性验证复核候选问题，并主动查找使判断不成立的条件。

- shape、dtype、layout 或时序相关问题必须给出具体触发条件，不能只写“可能出错”。
- 不报告无影响的个人风格偏好，不重复已存在的同一条意见，不把测试缺失直接当成功能错误。
- 区分源码分析、已执行验证和待验证假设。允许零条发现，不为凑数输出意见。
- 检视不自动包含修复源码。需要构建或测试时，依据目标版本的构建入口和测试配置选择验证方式；
  不以 Host 测试冒充 NPU 验证。

无法取得关键 diff、目标版本源码或适用规则文件时，列出未覆盖范围及原因；继续检视不受影响的部分，
将结果标为部分完成。构建或测试受环境限制时，单独记录验证缺口，不能据此判定功能错误。

### 4. 检查完成条件

形成最终报告前逐项核对：

- 模块选择覆盖实际影响范围；全部通用规则及所加载模块的全部规则都有覆盖记录，
  适用规则的全部相关改动已核对，不适用项有具体理由。
- 新增设施的必要性记录包含实际入口与消费者或外部交付依据；专用报错分支已与通用处理路径比较。
  只有内部互相调用、导出或测试引用，不能据此将必要性标为已核对且符合。
- 发现清单仅包含框架逻辑代码问题，未对已排除的 UT/ST 套用规则或生成意见。
- 每项已确认的本次新增或扩大违规均已进入发现清单，或关联 PR 中已有的同一条意见；
  同一根因可合并，但须保留涉及的规则及代码位置，不按问题数量或严重级截断。
- 未完成项及未决候选问题均已列出原因和剩余工作；任何规则缺项、无证据结论或未覆盖改动
  都不能标为已核对。存在这些缺口时只能报告部分完成，继续处理可完成的部分。

### 5. 输出或发布意见

先完成检视，形成可供用户审阅的完整意见（正文、文件和行号）、规则覆盖记录及验证说明。
GitCode PR 检视尚无发布授权时，先返回这些结果，再询问是否将意见更新到 PR，链接本 `SKILL.md` 并引用
“仅在用户明确要求或确认将检视意见更新到该 PR 后发布”的约定说明确认原因；收到明确答复前不发布。
用户在本次任务中已明确要求发布时，不重复询问；用户明确要求仅返回报告或不发布、
本地检视或没有待发布的确认问题时，不请求发布确认。
取得授权后执行 [GitCode 获取与提交说明](references/gitcode-workflow.md) 的发布步骤，
复用现有脚本，复查 head、对已有意见去重，并回读验证实际评论位置。
发布后仍返回发现清单、规则覆盖记录、验证情况及提交结果；发布受阻时说明具体原因和未提交意见。

## 输出约定

先给出全部已确认问题，按严重程度排序，再给出规则覆盖记录和验证情况。每条发现包括：

- `文件:行号`、级别（Blocker / Major / Minor）、类型（功能缺陷 / 规范违规）和简短标题；
- 适用或触发条件、代码证据、建议修改方向；功能缺陷说明影响，规范违规引用规则编号并链接原文。

级别按实际影响判断：阻止正常编译或执行、导致错误结果等重大问题优先；轻微且明确的规范问题可列为 Minor。
报告同时注明检视范围、PR head SHA（适用时）、已做验证及未验证事项。
检视框架逻辑代码时，无论是否发现问题，都须提供清单定义的规则覆盖记录，不能仅写“已参考规则”或“规范检查通过”。
本次约定范围已完成检视、规则覆盖记录无缺口且无确认问题时，说明“在本次范围内未发现有充分证据的问题”。
存在未覆盖范围时，说明已检部分的结论及剩余事项，不能把“未完成检视”表述为“没有问题”。
发布后逐条附评论 ID、位置、回读结果和 PR 链接；区分已确认、失败和未验证，成功部分不重复提交。
