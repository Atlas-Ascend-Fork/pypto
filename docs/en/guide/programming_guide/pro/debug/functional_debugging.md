# Functional Debugging

<!-- md-trans-meta sourceCommit=099ec62fdd650eea5fa0fd14533d5f0f32da389d translatedAt=2026-10-27T01:45:22.102Z pushedAt=2026-10-27T06:03:02.214Z nl=2 -->

When a functional issue occurs in a PyPTO Pro Kernel, first lock down the reproducible input Shape, data type, TilingKey, and `block_dim`, and then select a troubleshooting path based on the symptom: if a compilation error occurs on the first invocation, check the frontend exception and error code; if the Kernel executes normally but the result is incorrect, localize the precision issue; if an AI Core Error, timeout, or hang occurs during execution, collect the device-side exception information. Memory detection is a tool for troubleshooting suspected memory access issues and can be enabled as needed for the latter two types of issues.

After the issue is fixed, disable memory detection and remove temporary debug prints, recompile with the production configuration, and run regression tests covering the original failing case and the related Shape, data type, TilingKey, and `block_dim`.

## Compilation Errors

A Kernel decorated with `@pypto_pro.language.jit()` completes parameter binding, frontend parsing and validation, code generation, and compilation in sequence when a new compilation instance needs to be generated. First, check the user source code location, error description, and call stack in the exception to determine the failing stage. When parameter binding, Python frontend parsing, or IR validation fails, focus on checking the API parameters, Shape, data type, memory space, and compile-time constraints.

If the error carries a PyPTO error code, refer to the [Error Code Reference](../../../appendix/trouble_shooting/) to identify the component and check the suggested handling. The error location and error description remain the direct basis for locating issues in the user code. When code generation or toolchain compilation fails, also check the complete compilation log and generated code.

JIT compilation artifacts are located in the `build` directory under the current working directory by default. After `ASCEND_WORK_PATH` is set, they are located in the `${ASCEND_WORK_PATH}/PYPTO_PRO/build` directory. Pay attention to the following files:

| File | Purpose |
| --- | --- |
| `kernel.cpp` | Device-side Kernel source code generated by the compiler, which can be used to check parameter types, control flow, address calculation, and data movement. |
| `pipeline_generated.py` | Code for automatic inter-core pipeline scheduling generated after enabling [Automatic CV Parallel Pipeline](../advanced_programming/auto_parallel_pipeline.md), which can be used to check stage scheduling, preload, and inter-core synchronization. |

The files above are all diagnostic artifacts generated by the compiler. After locating the issue, modify the original Python Kernel and recompile it. Do not directly modify the generated files.

## Precision Error

When the Kernel executes normally but the output differs from the reference implementation, first confirm that the input, Shape, data type, layout, and comparison threshold are consistent, and read the result after device synchronization. Fix the failing case, and then follow the process provided by the [pypto-pro-precision-debug Skill](https://gitcode.com/cann/pypto-gym/blob/master/cannbot-skills/ops/pypto-pro-precision-debug/SKILL.md) to locate the first failing stage along the actual data path.

When it is necessary to check multi-core partitioning, loop boundaries, runtime parameters, or transfer offsets, [`pypto_pro.language.printf`](../../../../api/pro_api/Utils-API/debugging/printf.md) can be used to print scalar information such as the Core number, offset, Shape, and branch flags. In multi-core scenarios, it is recommended to use `pypto_pro.language.get_block_idx()` to restrict the Cores that print, avoiding heavy interleaving of logs. This API introduces runtime overhead and is intended only for functional debugging, not for performance testing.

If the results are disordered, errors occur intermittently, or out-of-bounds GM access, out-of-bounds Tile access, overlapping Tile memory ranges, or incorrectly paired mutexes are suspected, `@pl.jit(sanitizer=True)` can be set on the kernel function decorator to use the [memory detection tool](sanitizer.md) for assisted localization. When a problem is detected, the result is written to a report file. The coverage scope and usage constraints of the tool are described in that document. Memory detection introduces additional runtime overhead and should be disabled after the investigation is complete.

## AI Core Error

Kernel dispatch is an asynchronous operation. During debugging, synchronize the stream after launch so that device-side exceptions are exposed at the current call point, and retain the complete error information and runtime logs:

```python
kernel[None, block_dim](*args)
torch.npu.synchronize()
```

After a kernel triggers an AI Core Error such as an out-of-bounds read/write or a deadlock timeout on the device, you can restore the scene using the exception dump and offline reproduction tools, and locate the Error PC to the kernel source line. Before running the test case, set a writable working directory:

```bash
export ASCEND_WORK_PATH=./wk
```

Before collection, ensure that `NPU_COLLECT_PATH` is not set. If it is already set, run `unset NPU_COLLECT_PATH` to cancel it; otherwise, the data files required for offline reproduction cannot be generated. It is recommended to run the problematic test case in a separate subprocess to ensure that the exception data is generated completely.

After the exception occurs, the related files are saved in the following directory:

```text
${ASCEND_WORK_PATH}/extra-info/data-dump/<device_id>/
```

The main files include:

| Artifact | Purpose |
| --- | --- |
| dump data file | Saves the Shape, data type, and raw data of the input, output, and workspace tensors. |
| `<kernel>_launch_args.json` | Saves the kernel name, `block_dim`, and the complete pointer and scalar launch arguments. |
| `<kernel>_call_kernel.so` | The kernel executable with debug information, used for offline reproduction and source line location. |
| `call_kernel_<digest>.so` | A copy of the original JIT artifact, used for comparison and high-fidelity reproduction. |
| `kernel.cpp`, `call_kernel.cpp`, and related header files | Source code copies corresponding to the exceptional kernel. |

Use the following command to parse the dump and reproduce the exception:

```bash
python tools/scripts/debug_aicore_error_pro_repro.py \
    -p <dump_dir> \
    [-d <device_id>] \
    [-out <output_dir>] \
    [-t <seconds>]
```

Here, `-p` points to the `extra-info/data-dump/<device_id>` directory; `-d` is used to override the Device ID parsed from the directory name; `-out` specifies the report output directory; and `-t` sets the timeout for a single reproduction, with a default value of 600 seconds.

The tool restores the tensor data and kernel launch arguments, generates and executes a single-operator reproduction script, and then extracts the Error PC from the plog of this run. The main outputs include:

- `test_single_op.py`: a standalone single-operator reproduction script that can be executed independently.
- `reproduction_report.txt`: reproduction result, faulty core, Error PC, symbol, source line, inline call chain, and source context.
- `reproduction_report--singlecommit.txt`: singlecommit diagnosis result for timeout-type faults. It is generated only for timeout-type faults.

For timeout-type faults, the tool automatically reruns in singlecommit mode. If the execution succeeds in singlecommit mode, the issue is related to inter-core concurrency or synchronization timing. If it still fails, continue troubleshooting based on the stuck core and source location in the report.

If the report indicates `Error PC not found in plog`, check whether CANN has generated the symbol locator log and whether the log directory is configured. If the report indicates that the source line cannot be resolved, check whether `ASCEND_HOME_PATH` and the BiSheng toolchain are available. When the old dump lacks `<kernel>_launch_args.json`, the tool falls back to `block_dim` of `1`, and issues that depend on multi-core concurrency may not be reproduced as in the original scenario.

If a memory access issue is suspected based on the exception location, try enabling the [memory detection tool](sanitizer.md) to assist troubleshooting. If the tool detects no issue, continue checking synchronization, address calculation, and the Kernel source code based on the exception report.
