# SuperKernel

## Description

SuperKernel is an operator binary fusion technique: during the graph compilation phase, multiple compiled subcore functions are fused into a single super kernel function to reduce task scheduling and dispatch overhead. The fused subcores share a single dispatch, and dependency handover between adjacent subcores is completed through inter-core synchronization events.

PyPTO Pro declares the SK capability of a Kernel through the `sk_cap` parameter of `pypto_pro.language.jit`. After it is set, JIT additionally generates the `__sk__` entry and `SK_BIND` record in the Host-side Launcher, and appends the SK-related header file paths and compilation macros during the compilation phase. The content of kernel.cpp is the same as that of a normal build. Whether a Kernel is fused is determined by the graph layer: when it is not fused, it is executed as a normal Kernel, and the early-start API has no effect.

## Usage

### Declaring SK Capability (sk_cap)

In pypto_pro.language.jit, declare the capability bits through sk_cap. The value is a member of pypto_pro.language.SkCap or a bitwise OR combination of its members. Only enum members are accepted, not raw integers. For the bit value and meaning of each capability bit, see [JIT Compilation: JIT Decorator Parameters](../development/compilation_and_execution/JIT_compilation.md#jit-decorator-parameters).

```python
import pypto_pro.language as pl


@pl.jit(auto_mutex=True, sk_cap=pl.SkCap.CAP_4_DISABLE_DCCI_ALL)
def exp_tile_kernel(input_tensor, output_tensor):
    ...
```

### Enabling SuperKernel in torch.compile <a id="enable-superkernel"></a>

SuperKernel optimization must also be enabled on the graph compilation side. When compiling through the npugraph_ex backend, set super_kernel_optimize=True in the options of torch.compile:

```python
model = torch.compile(
    module,
    backend="npugraph_ex",
    options={"super_kernel_optimize": True},
)
```

To control the fusion scope, use the torch.npu.super_kernel_scope_begin and torch.npu.super_kernel_scope_end pair of APIs to mark the subgraph that participates in fusion: the two APIs must be used in pairs with identical scope identifiers, and the operators marked with the same scope between them participate in SuperKernel as a single fusion scope.

```python
class Model(torch.nn.Module):
    def forward(self, x):
        torch.npu.super_kernel_scope_begin("sk_scope")
        y = exp_tile_op(x)  # PyPTO Pro subcore participating in fusion
        y = y + 1.0         # torch operators within the same scope also participate in fusion
        torch.npu.super_kernel_scope_end("sk_scope")
        return y


model = torch.compile(
    Model(),
    backend="npugraph_ex",
    options={"super_kernel_optimize": True},
)
```

### Early-Start Interaction <a id="early-start"></a>

When there is an overlapable dependency between adjacent subcores, use the paired early-start APIs to run instructions at specified positions in parallel with the adjacent subcores:

| API                                          | Description                                                             |
| ----------------------------------------------- | ------------------------------------------------------------------ |
| pypto_pro.language.system.wait_pre_task_end   | Instructions before the call point can run in parallel with the preceding subcore. Use it together with CAP_1_EARLY_START_WAIT. |
| pypto_pro.language.system.set_next_task_start | Instructions after the call point can run in parallel with the following subcore. Use it together with CAP_2_EARLY_START_SET.  |

- The two APIs act on the two sides of the same boundary between subcores and should be used together in adjacent subcores: the preceding subcore calls set_next_task_start, and the following subcore calls wait_pre_task_end. During SK graph compilation, synchronization tasks are generated by pairing adjacent subcores. If they are not paired, the synchronization task degrades to an empty synchronization and produces no overlap effect.
- Each core and each TilingKey branch must call the API exactly once. Avoid calling it under different conditions in runtime if/for statements. All TilingKey branches that may run should call the API; otherwise, a mismatch in the number of synchronization instructions may cause a hang.
- The force parameter is a compile-time bool constant and defaults to True. In the SK subcore context, the non-forced form is optimized away during compilation.

For details, see [pypto_pro.language.system.wait_pre_task_end](../../../../api/pro_api/SIMD-API/synchronization/wait_pre_task_end.md) and [pypto_pro.language.system.set_next_task_start](../../../../api/pro_api/SIMD-API/synchronization/set_next_task_start.md).

### Scheduling Mode (schedmode)

When schedmode=1, the JIT generates the `__schedmode__(1)` qualifier (batch mode) at the `__global__` entry. If pypto_pro.language.system.sync_all() is used in the kernel and multiple streams run concurrently, it is recommended to set schedmode to 1 to reduce the risk of deadlock. For an operator that does not actually call full-core synchronization but has schedmode=1 set, if it needs to be fused with an operator launched with a larger number of cores, set CAP_8_DISABLE_BATCHMODE_CHECK to skip the schedmode validation.

### Scaling the Number of Cores by Container

After CAP_16_BLOCKDIM_SCALE_UP is set, the kernel is launched with the number of cores of the fusion container. Inside the kernel, use pypto_pro.language.get_block_num() to dynamically determine the actual number of cores. Do not assume that the number of cores equals its own configured value. The operator must ensure that it still executes correctly when the actual number of launched cores is greater than its original number of cores.

### SIMT VF Adaptation <a id="simt-vf-adaptation"></a>

When the SIMD outer layer calls a SIMT VF, the VF must not read `pypto_pro.language.simt.grid_dim()` or `pypto_pro.language.simt.block_idx()`. The outer SIMD layer should use `pypto_pro.language.get_block_num() * pypto_pro.language.get_subblock_num()` and `pypto_pro.language.get_block_idx()` to compute the number of cores and the core index, and pass them into the VF as scalar parameters; the helper call chain must continue to pass these parameters along.

## Constraints

- When the SIMD outer layer calls a SIMT VF, the VF must not retain cross-core reads of `pypto_pro.language.simt.grid_dim()`/`pypto_pro.language.simt.block_idx()`; otherwise, under an SK container, container-level core count or core index may be used.
- A pure SIMT Kernel does not support direct participation in SuperKernel fusion: after fusion, subcores are launched according to the container grid, and the values read inside the Kernel through `pypto_pro.language.simt.grid_dim()`/`pypto_pro.language.simt.block_idx()` are the container-level thread block count and index, which are unreliable (potentially causing precision errors or out-of-bounds access). If fusion is required, rewrite it into the SIMD-calls-SIMT-VF mode (see the [SIMT VF Adaptation](#simt-vf-adaptation) section).
- SuperKernel optimization must be enabled on the graph compilation side for fusion to actually occur (see the [Enabling SuperKernel in torch.compile](#enable-superkernel) section).
- The two early-start APIs should be used together in adjacent subcores; see the [Early-Start Interaction](#early-start) section.
- sk_cap must be a member of pypto_pro.language.SkCap or a bitwise OR combination of its members; passing a raw integer or an invalid bit will be rejected by the frontend.
